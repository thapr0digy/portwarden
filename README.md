# Portwarden

A Go agent with C eBPF programs that reports listening TCP sockets and explicitly bound UDP sockets, in every network namespace (host and containers), to NATS JetStream, with the program, systemd unit and container that hold each one, how exposed each one is (bind address, host firewall, Docker and Kubernetes port mappings), which reverse-proxy routes (nginx, Apache, HAProxy) end at it, and the server's public-IP candidates. The backend (M5) keeps the current state in PostgreSQL behind a read-only API (`portwarden-inventory`, which also runs the cloud look-up for level 3), pages on newly reachable listeners and silent hosts (`portwarden-alerter`), and confirms exposure from outside (`portwarden-verifier`, level 4); see "Backend".
Kernel floor 6.8 (Ubuntu 24.04+).

M2 decisions (where the design left room): container network namespaces are reported, each listener carrying its netns (the foreign-netns filter is gone, and the heartbeat's `dropped_foreign_netns` stays only as a deprecated field, always 0); there are no exec or exit tracepoints, so each event carries the cgroup id read in the hook, which still yields unit and container after the process is gone, while exe, cmdline and sha256 come from `/proc` when the process is still there; UDP opens use `fexit/udp_lib_get_port` with a nonzero requested port rather than a cgroup bind program, so client autobinds and `bind(:0)` are not listeners and no `CAP_NET_ADMIN` is needed; a restart is an `owner_changed`, because a close is held for a grace window (`--close-grace`, 2 s) and a reopen of the same key inside it replaces the owners; a recheck every 5 minutes (`--recheck`, and early when ring-buffer drops rise) reconciles a fresh dump and publishes the periodic snapshot; and a size-capped disk spool (64 MiB under `/var/lib/portwarden/spool`, oldest segment dropped when full) replaces the memory queue, so messages survive NATS outages and agent restarts with their original timestamps.

M3 decisions: exposure levels 0–2 are judged on the server from the bind address, the interfaces and the host firewall, read with `nft -j list ruleset` plus `iptables-save`/`ip6tables-save` and evaluated by a three-valued rule evaluator (see "Exposure"); levels 3 and 4 are reserved in the enum for the backend (M5). A container listener takes the exposure of the host port a mapping (a DNAT rule found by simulating packets, or a docker-proxy command line) points at it, and is local only when the rules are fully readable and nothing could map it. A failed or partial firewall read keeps every listener's last known level and is reported as a host condition. Firewall changes arrive as nf_tables netlink notifications and address changes as rtnetlink notifications (each burst read 1 s after it settles, at most 5 s after it starts); without notifications, or with an iptables-legacy ruleset, the firewall is polled (`--firewall-poll`, 30 s); the recheck rebuilds everything. Public-IP candidates come from interface addresses, cloud metadata (AWS IMDSv2, GCP, Azure, only when DMI names that cloud) and the local address of the agent's NATS connection when it is public. No third-party "what's my IP" service is used.

M4 decisions: proxy routes come from the proxies' configuration files, read by the agent itself with each proxy's own include rules, never by running the proxy (`nginx -T` fails unprivileged on stock Ubuntu and on any TLS host, and running a binary found through `/proc/<pid>/exe` with the agent's capabilities would be a privilege-escalation path); the recorded dumps (`nginx -T`, `apache2 -S`, `apache2 -t -D DUMP_INCLUDES`, `haproxy -c`) are the test oracle instead. This supersedes the design's "use each proxy's own full dump" (§3, §9): the mitigation for parser gaps is the fixture set plus inferred routes from observed traffic. A config is read only for a trusted proxy (root master, root-owned executable and config files that only root may write), and what is published is bounded and redacted (see "Proxy mapping"). nginx and Apache are parsed fully, HAProxy's frontends and backends from its config (no runtime API); Caddy, Envoy and Traefik are known from their observed connections only, labelled inferred. Observed connections come from `cgroup/connect4`/`connect6` programs attached only to the proxies' own cgroups and filtered in the kernel to the proxies' processes and their children, counted per destination in a map. A route set is re-read when a config file (or a directory an include globs) changes and holds still for 2 s, when the proxy restarts, and on the recheck; no signal probe (a reload without a file change changes no route). Each route is joined to the listener table, so it ends at a real program; see "Proxy mapping".

M5 decisions: the backend is three binaries, each with its own nkey NATS user minted by `portwarden-natsauth` (hosts may publish only `asm.<host>.>`; each service reads only through its own named durable consumers). The cloud look-up runs inside the inventory and publishes level 3 on `pwb.cloud.<host>.exposure`; the inventory asks the verifier to probe on `pwb.probe.<host>.request` (built from its stored state), and the verifier answers on `pwb.verifier.<host>.exposure`. No host may publish under `pwb.`, and consumers take origins from subjects only. Backend events carry their own `run_id` and `seq` 0, so they never look like gaps in a host's sequence. The inventory reloads a host's latest snapshot from the stream when a gap is covered by it, else marks the host `needs_resync` until the next snapshot; it orders a host's runs by boot id and a persisted run counter, not by clock. A message that can never be applied is quarantined, never retried forever. The alerter keeps its decisions and an outbox of pages in PostgreSQL, so pages survive webhook outages and restarts. (The fix wave after the M5 review introduced the `pwb.` namespace, run numbers, quarantine, the probe requests and the alerter's outbox; see `.superpowers/program/m5-report.md`.) Config files are JSON. AWS was the only cloud implemented (GCP and Azure followed in M10 phases 2 and 3); GCP and Azure hosts got "unsupported provider: no level 3 evidence". No real cloud account was used: the AWS code is tested against recorded API responses.

M6 decisions (hardening): the agent checks itself every 30 s with fixed rules (its eBPF links still attached and running the programs it loaded, by program id and tag; no ptrace tracer on any of its threads; its executable and systemd unit files hashing as they did at start; its kernel drop counter never going down) and publishes each raised or cleared flag on `asm.<host>.tamper`, with the current status on every heartbeat; the alerter pages once per newly raised flag (see "Tamper signals"). The agent unit is hardened down to `systemd-analyze security` 2.5 (was 6.7) with a seccomp allow-list (`@system-service` plus `bpf` and `perf_event_open`) and still only the four capabilities. `make dist` builds byte-reproducible static binaries for amd64 and arm64, `.deb`s for the agent and the backend, SBOMs and checksums; `deploy/` adds a Dockerfile, a DaemonSet and a Helm chart (see "Packaging and install"). `make matrix` runs the kernel tests on Ubuntu 24.04 (6.8), Ubuntu 26.04 (7.0) and x86_64; CI runs the same legs in VMs (see "Kernel test matrix"). Before testing on an x86_64 machine, follow "x86 test checklist".

### Fuzzing

Each parser of untrusted input has a native Go fuzz target (no extra tool), seeded from the package's testdata or test cases: `nft -j` JSON (`internal/exposure/nft` `FuzzParse`), `iptables-save` (`internal/exposure/iptables` `FuzzParse`), the nginx, Apache and HAProxy loaders (`internal/proxy/{nginx,apache,haproxy}` `FuzzLoad`, whose input is a file tree packed as `path NUL content NUL …`, the first path being the main config; see `conf.DecodeFiles`), command-line redaction (`internal/redact` `FuzzCmdline`), spool records and segment recovery (`internal/spool` `FuzzDecodeRecord`, `FuzzOpen`), and the inventory's decode and quarantine path (`internal/inventory` `FuzzHandle`, two messages per input on one consumer; every error must be permanent). Each input must not panic, must stay within a time and allocation budget (`internal/fuzzcheck`; `PORTWARDEN_FUZZ_REPORT=1 go test -v -run '^Fuzz' ./...` prints each seed's share of it) and the parser's own output caps; the proxy loaders' `TestLoadAtTheReadLimitFitsBudgetAndMemory` checks that a config at the read limit fits that budget and grows the heap by at most 85 MiB.

`make fuzz` runs every target briefly (`FUZZTIME`, default 30 s; `FUZZMINIMIZETIME`, default 10 s, bounds the shrinking of each new input). Deep runs stay manual, one target at a time, for as long as you like:

```
go test -run '^$' -fuzz '^FuzzLoad$' -fuzztime 1h ./internal/proxy/nginx
```

(`-parallel N` sets the workers, default GOMAXPROCS.) The growing corpus lives in `$(go env GOCACHE)/fuzz` and is not committed. A failure writes its input to `<package>/testdata/fuzz/<Target>/<hash>`: fix the parser, commit that file with the fix, and `go test ./...` replays it from then on (`go test -run '<Target>/<hash>' ./<package>` replays it alone).

`gen/asm/v1/events.pb.go` is committed, so `go build ./...` works on macOS without `buf`.
`bpf/vmlinux.h` is produced in the VM with `bpftool btf dump file /sys/kernel/btf/vmlinux format c`.

## Event schema

`proto/asm/v1/events.proto` (package `asm.v1`): `ListenerEvent`, `Snapshot`, `Heartbeat`, `ExposureEvent`, `HostEvent`, `ProxyRoutes`, `ExposureConfirmation`, `TamperEvent`, `HostForgotten`.
Subjects: `asm.<host>.listener.opened`, `.listener.closed`, `.listener.owner_changed` (its `ListenerEvent` carries the new `processes` and the old `previous_processes`), `.exposure.changed`, `.host.changed`, `.proxy.routes`, `.snapshot`, `.heartbeat`, `.tamper`; the backend's own: `pwb.cloud.<host>.exposure`, `pwb.verifier.<host>.exposure`, `pwb.probe.<host>.request`, `pwb.inventory.<host>.forgotten` (see "Backend").

- `ListenerEvent.exposure` (11) is the listener's exposure when the event was published (on `closed`: its last one). `ListenerEvent.host` (12), `Snapshot.host` (7) and `ExposureEvent.host` carry the host block; `ListenerState.exposure` (3) puts each listener's exposure in the snapshot. Every M3 field has a new number; nothing earlier changed.
- `Exposure { level, evidence[] }`. `ExposureLevel` is the design's level plus one, so that 0 stays "unset": `EXPOSURE_LOCAL` (level 0), `EXPOSURE_BOUND` (1), `EXPOSURE_HOST_FIREWALL_OPEN` (2) and, reserved for M5, `EXPOSURE_CLOUD_OPEN` (3) and `EXPOSURE_CONFIRMED` (4).
- `exposure.changed` (`ExposureEvent`: listener, processes, `exposure`, `previous`, `trigger`) is published once when a listener opens (`previous` unset, `trigger=opened`, right after its `listener.opened`) and whenever its level changes later (`trigger` is `firewall`, `interfaces`, `recheck`, or `listener` when another listener's change moved it, e.g. a port mapping's proxy appeared). A change of evidence alone is not an event; it shows in the next event or snapshot. A restart inside the close grace keeps the level silently. The baseline snapshot carries every listener's exposure and causes no `exposure.changed`, as it causes no `opened`. Alert on `asm.*.exposure.changed` where `exposure.level >= EXPOSURE_HOST_FIREWALL_OPEN`, and also compare each `snapshot`'s exposures with the previous run's: a listener whose exposure changed while the agent was down (upgrade, restart) shows up only in the snapshot that starts the next run.
- `host.changed` (`HostEvent`: `host`, `previous`) is published when the public-IP candidates or the cloud identity change after startup. `HostInfo { public_ips[] {ip, via, dir, iface}, cloud, instance_id, conditions[] }`; `conditions` (4) lists what the agent cannot read in full, e.g. `fw:unreadable iptables-save: Permission denied`, and empties again on recovery, each change being one `host.changed`; `via` is `netlink` (an interface address, `dir=in`), `imds` (cloud metadata, `dir=in`) or `ingest-local` (`dir=out`); see "Public IP".
- `proxy.routes` (`ProxyRoutes`: `proxy`, `routes[]`, `trigger`, `removed`, `host`, `truncated`, `total_routes`) carries one proxy's route set, at most 500 routes and at most half the server's `max_payload` (read at connect, 1 MiB by default) per message: a larger set keeps its first routes in order with `truncated=true` and `total_routes`. One proxy gets at most one `proxy.routes` per 10 s (a change inside that interval goes out when it ends, with the reason it was first held for; removals go out at once). It is published when the proxy is first seen (`trigger=started`), when its routes change because its config changed (`config`), because a listener changed (`listener`: the proxy restarted, or a backend opened, closed or changed owner), because a backend was first seen in traffic or an unconfigured destination appeared (`traffic`), or on the recheck (`recheck`), with `removed=true` (`stopped`) when the proxy is gone, and after every snapshot (`snapshot`). Connection counters alone are no event: they are current in the route sets that follow each snapshot. `Proxy { id, kind, processes (master first, at most 16), process_count, listeners, config_path, config_files, notes }`; `id` is `<kind>/<netns>/<config path>` (plus `@<container id>` for a proxy in a container), stable across reloads and restarts. `ProxyRoute { listen[], frontends[], server_names[], path, kind, target, upstream, root, source, inferred, notes[], backends[] }`: `kind` is `proxy`, `fastcgi`, `uwsgi`, `scgi`, `grpc`, `memcached`, `static` or `return`; `source` is `file:line`. `ProxyBackend { address, ip, port, unix_path, listener, processes, config, seen, connections, last_seen, note }`: `config` = named in the config, `seen` = the proxy connected to it (an observed backend that is not configured is in an `inferred` route), `listener`/`processes` = the listener it ends at, `note` says why it is not resolved or joined (`unresolved: variable $host`, `unresolved: hostname db.internal (no DNS lookups)`, `no listener`, `backup`).
- M5 (all new numbers): `HostInfo.region` (5) is the cloud region from metadata (AWS `placement/region`, the GCP zone's region, the Azure `location`), which the cloud look-up needs. `ExposureEvent.origin` (12) is empty for the agent and `cloud` for the backend's level 3 verdicts on `pwb.cloud.<host>.exposure` (informational: consumers take the origin from the subject; `level` `EXPOSURE_CLOUD_OPEN` with evidence such as `cloud: sg-0abc (web) allows tcp/443 from 0.0.0.0/0`, or, when a listener stops being open in the cloud, its agent level with the reason; `trigger=cloud`). `pwb.verifier.<host>.exposure` carries an `ExposureConfirmation { listener, result, target, probe, banner, detail, rtt_ms, checker, exposure, origin=verifier }`: `result` is `confirmed` (`exposure` is then `EXPOSURE_CONFIRMED` with the probe as evidence), `unreachable` (TCP refused or timed out, or an ICMP port unreachable for UDP) or `no_response` (UDP silence: open or filtered, never closed). Backend events have their service's own `run_id` (`cloud-<ulid>`, `verifier-<ulid>`) and `seq` 0: they are not part of the host's sequence, and gap trackers skip them. `ProbeRequest { listener, level, addresses (≤4), ports (≤4), proto, reason }` is the inventory's request to the verifier. Fix wave: every agent message type carries `boot_id` and `run_number` (the kernel boot id and a counter kept in the spool directory), by which consumers order a host's runs.
- M7 (new numbers, `optional`): `HostInfo.firewall_fingerprint` (6) and `Heartbeat.firewall_fingerprint` (12), a digest of the agent's parsed ruleset (see "Exposure", firewall fingerprint).
- M10 (new number): `HostInfo.cloud_resource` (7), the instance's full name in its cloud for the backend's GCP and Azure look-ups: GCP `projects/<project>/zones/<zone>/instances/<id>`, Azure the VM's resource id (`/subscriptions/<id>/resourceGroups/<group>/providers/Microsoft.Compute/virtualMachines/<name>`). Empty on AWS, off-cloud, when the metadata server does not say, and from older agents. A change publishes `host.changed`. The value comes from the host, so the inventory checks it at ingest: at most 512 bytes, its cloud's exact shape (GCP project id, zone and a numeric instance equal to `instance_id`; Azure a UUID subscription, a group name of 1–90 Unicode letters, marks, digits, `_`, `-`, `.` and `()` not ending in `.`, an ASCII VM name, and an `instance_id` that is a UUID, the VM's `vmId`); anything else is dropped (stored empty) and logged once per distinct value per host (at most 4096 hosts remembered; never the value itself). The Azure resource id names the VM, not its `vmId`, so the inventory cannot match the instance: the Azure look-up (M10 phase 3) must read the VM by the parsed id and require its `properties.vmId` to equal `instance_id` (case-insensitive), else judge nothing (undetermined). The GCP and Azure look-ups (M10 phases 2 and 3) will also require the project or subscription to be on a configured allow-list, call only their fixed API hosts, and build request paths from the parsed parts, never from the raw string.
- M11 (new numbers): `Heartbeat.agent_version` (13) and `Heartbeat.exe_sha256` (14), and the same as `HostInfo.agent_version` (8) and `HostInfo.exe_sha256` (9): the agent's release version (`internal/version`, `dev` in a plain `go build`) and the lowercase hex SHA-256 of its running executable (`/proc/self/exe`, hashed once at start, never on the event loop; the `self_exe` tamper check reuses it as its baseline). `exe_sha256` is empty when the agent could not read its own executable (logged at start), and both are empty from older agents. `HostEvent.stopping` (10) marks the agent's clean-shutdown marker: on SIGTERM/SIGINT the agent publishes a `host.changed` with `stopping` set and `host` equal to `previous`, before it drains the spool (see "Running the agent"). Both are self-reported, a visibility aid and not attestation: see "What root can still do".
- M8 (a new message): `HostForgotten { event_id, host_id, at }` on `pwb.inventory.<host>.forgotten`, published by the inventory when an operator forgets a host (see "Forget a host"). `Process.cmdline` is now published with secret arguments masked (see "Command-line redaction").
- `ListenerEvent.behind_proxy` (13) and `ListenerState.behind_proxy` (4) list the routes that end at the listener (`ProxyRef { proxy_id, kind, proxy (the master), frontends, server_names, path, config, seen }`), as of publish time; on `closed`, the routes it had. `Snapshot.proxies` (8) lists every proxy as `ProxyState { proxy, route_count, routes_digest, truncated }` without its routes (so a snapshot never grows past `max_payload` with the proxies); each proxy's route set follows the snapshot as a `proxy.routes` with `trigger=snapshot`, and `routes_digest` (hex SHA-256, first 16 bytes, of the deterministic encoding of the routes) tells whether one already held is current. `behind_proxy` lists at most 32 routes per listener and is refreshed only on that listener's events and in snapshots: `proxy.routes` is authoritative. All M4 fields are new numbers.
A listener's identity is `netns/proto/addr:port`, e.g. `4026531840/tcp/0.0.0.0:8080` or `4026531840/tcp/[::]:8080`;
IPv4-mapped IPv6 addresses are unmapped first. See `internal/model`.

## eBPF probes

`bpf/listen.bpf.c`, loaded by `internal/probes` (bindings generated by `bpf2go` via `make generate`; `listen_bpfel.go` and `.o` are committed). The committed objects (`internal/probes/*_bpfel.o`, `internal/baseline/*_bpfel.o`) are what `go generate` produces in the Ubuntu 24.04 dev VM (`dev/lima.yaml`): clang 18.1.3 (Ubuntu 1ubuntu1), libbpf-dev 1.3.0-2build2 (headers), bpf2go from cilium/ebpf v0.22.0. Regenerating there leaves `git status` clean; another clang may produce different bytes.
They watch every network namespace; each event carries the socket's netns inode and the calling task's cgroup id.
None of these programs runs per connection or per packet (the proxy connect programs below run per connection, but only in proxies' cgroups); the two UDP hooks run once per UDP socket bind and close (client sockets included) and return after one field read unless the socket was bound to an explicit port.

| Hook | Emits | Why this hook |
| --- | --- | --- |
| `fexit/inet_csk_listen_start` | `opened`, only when it returned 0 and the socket is TCP | The port is assigned inside this function, so `fexit` sees the real port. The `inet_sock_set_state` tracepoint fires before that (port 0 for an unbound socket) and also for listens that then fail. |
| `fentry/inet_csk_listen_stop` | `closed`, for TCP | In 6.8 it runs only when a listener is torn down: `close()` (via `__tcp_close`) and `shutdown(SHUT_RD)` (via `tcp_disconnect`). The `inet_sock_set_state` tracepoint would run on every TCP state change of every connection just to catch LISTEN→CLOSE. |
| `fexit/udp_lib_get_port` | `opened`, for UDP, only when it returned 0 for a nonzero requested port | An explicit `bind()` passes the requested port; autobind (`connect`/`sendto` on an unbound socket) and `bind(:0)` pass 0, so client sockets are skipped. The address is set before `get_port` and the port on success. |
| `fentry/udp_lib_unhash` | `closed`, for UDP sockets with `SOCK_BINDPORT_LOCK` | The lock is set only by a bind to a nonzero port. `fentry` because unhash zeroes the port. `udp_disconnect` never unhashes a socket with that lock, so `connect()` after `bind()` is not a close. |

- A `closed` event carries only the socket cookie, netns and process: by the time `inet_csk_listen_stop` runs, `__inet_put_port` has released the port. The state table closes listeners by cookie.
- A failed `listen()` (e.g. `EADDRINUSE`) resets the socket state without calling `inet_csk_listen_stop`, so it produces no event at all.
- Events lost to a full ring buffer are counted (`Probes.Counters`).
- UDP-Lite sockets run the UDP hooks too; the protocol check excludes them.
- If a cgroup `post_bind` program rejects a UDP bind after `get_port` succeeded, the kernel releases the port without an unhash, so the listener stays reported until the next recheck closes it.

`bpf/proxyconn.bpf.c`, loaded by `internal/probes` (`ProxyConns`), counts the connections reverse proxies make:

| Hook | Records | Why this hook |
| --- | --- | --- |
| `cgroup/connect4`, `cgroup/connect6` | per (proxy tgid, destination address and port): a count and the last time, in an LRU hash (16 384 entries); TCP only; every connect is allowed | Attached (bpf_link, multi-attach) only to the cgroups the proxies run in (e.g. `/system.slice/nginx.service`, a container's scope), so no other process runs it (e2e: 0 runs for 10 000 non-proxy connections). In the kernel it counts only when the caller or its parent (a worker under its master) is in `proxy_tgids`, which the agent fills with each proxy's master and holders. The destination is the address the proxy asked for, before any NAT. |

Edge cases:

- MPTCP listeners show up as their TCP subflow socket.
- DCCP also calls `inet_csk_listen_stop`; the protocol check excludes it.
- `shutdown(SHUT_RD)` on a listener, then `listen()` again, reuses the same socket cookie: the table sees a close then an open.

## Baseline snapshot

`internal/baseline.Snapshot()` lists every TCP listener and every UDP socket bound to an explicit port, in every network namespace, once at agent start, as `source=baseline` `opened` observations.

- TCP sockets (host netns): a hand-built `SOCK_DIAG_BY_FAMILY` dump (`golang.org/x/sys/unix`, no netlink library) for `AF_INET` and `AF_INET6` with `idiag_states = 1<<TCP_LISTEN` only, so the kernel walks the listening hash and never the established one. Needs no capability. A reply flagged `NLM_F_DUMP_INTR` is retried up to 3 times, then fails.
- UDP sockets (host netns): `bpf/udp.bpf.c`, an `iter/udp` program run once that writes `{cookie, family, port, addr}` per socket with `SOCK_BINDPORT_LOCK` (bound to a nonzero port; autobound and `bind(:0)` client sockets are skipped). It walks only the agent's netns, and is the only source for kernel sockets such as VXLAN's or WireGuard's, which have no file and so no owner.
- Owners: `bpf/owners.bpf.c`, an `iter/task_file` program run once (`link.AttachIter`, read to EOF) that writes `{cookie, cgroup_id, tgid, uid, netns, family, proto, port, addr, comm}` per TCP listening or explicitly bound UDP socket per process, in any netns; `cgroup_id` is `task->cgroups->dfl_cgrp->kn->id` and `exe` is read from `/proc/<pid>/exe`. Host sockets are joined to the dumps by socket cookie: one observation per socket per owning process, one with an empty process for kernel sockets (nfsd, ksmbd, VXLAN). Sockets in other netns (containers) are keyed from the owner records alone, so ownerless sockets there (kernel sockets inside a container netns) are not listed.
- Order: a cookie-assigning TCP dump, then owners, then the TCP and UDP dumps that are reported. A socket that appears after the owners were read is reported without an owner (the live probe has its `opened` with the owner).
- MPTCP (Go's default for listeners): the fd holds the MPTCP socket, but inet_diag and the probe see its first TCP subflow, so the iterator reports the subflow's cookie. On 6.8 it can only read that cookie (via `bpf_rdonly_cast`), not assign it, and the kernel assigns cookies lazily; the first dump assigns them, but only in the host netns. An MPTCP listener in another netns that was opened while no probe ran (before install, during agent downtime) therefore has no subflow cookie; the iterator reports it under the MPTCP socket's own cookie (also global and unique), which the baseline and every recheck use. The live probe reports the subflow's cookie, so such a listener's close is not matched and is reported by the next recheck (within 5 minutes). A restart of it in the same netns is not `closed` plus `opened` either: the new socket joins the key while the old cookie still stands, giving an `owner_changed` that lists both the old and the new PID, and the next recheck then publishes a second `owner_changed` that drops the dead PID. `SO_COOKIE` on an MPTCP fd returns the MPTCP socket's own cookie, not the subflow's.

## Exposure

`internal/exposure` judges every listener whenever a listener changes and whenever a new view of the host (firewall and interfaces) is read. Evidence lists why, in order, for example `["bind:any", "nft: accept tcp/8443 from 0/0 (eth0, inet filter input)"]`.

| Level | When |
| --- | --- |
| `local` | Bound to loopback (`bind:loopback`), or a listener in another netns that provably nothing maps (`netns: no host port mapping`): its addresses were read, the rules were read in full, no DNAT targets it, and none of the mechanisms the simulation cannot follow is present (see below). |
| `bound` | Bound to `0.0.0.0`/`::` (`bind:any`) or to an interface address (`bind:192.168.5.15 (eth0)`), but the firewall does not let anyone in, or cannot tell (`iptables: drop tcp/80 from 0/0 (eth0, policy ip filter INPUT)`, with `restricted by source (<chain>)` when an accept skipped it only because the source is not listed; `fw:undetermined quota (nft: tcp/7000 from 0/0, eth0)`; `fw:unreadable …`; `firewall: no external interface`). An address on a container network interface (`docker0`, `br-*`, `cni0`, …), on no interface, or on a down interface is `bound` and not judged further. A listener in another netns with a public address is `bound` (`netns: public address …`). |
| `host_firewall_open` | A new connection from any outside address (0/0) to at least one external address of the host reaches the port on every path through the rules. No filtering at all counts as open. |

The question asked of the firewall: does the first packet of a new TCP connection or UDP flow, from an arbitrary outside address and port, to address A on interface I, port P, get through? It is asked for every address of every external interface (up, not loopback, not a container network by name: `docker`, `br-`, `veth`, `cni`, `flannel`, `cali`, `cilium`, `lxc`, `lxdbr`, `kube-`, `weave`, `virbr`, `vnet`, `podman`, `tunl`, `vxlan`, `genev`, `nodelocaldns`; link-local addresses skipped). A `0.0.0.0` listener is asked for IPv4, a `::` listener for IPv4 and IPv6 unless its socket is `IPV6_V6ONLY`, a specific address for that address only. One open answer is enough for level 2.

`IPV6_V6ONLY` is read per socket, from the kernel: the listen probe, the owners and UDP iterators read `skc_ipv6only`, and the inet_diag dump's `INET_DIAG_SKV6ONLY` attribute (which the kernel adds to every IPv6 reply). The flag is fixed once a socket is bound (binding a specific IPv6 address sets it). A `[::]` key with several sockets (`SO_REUSEPORT`) is v6-only only when all are; one dual-stack socket takes IPv4 for the key. A v6-only `[::]` listener reads `bind:any (IPv6 only)` and is judged for IPv6 alone (`firewall: no external interface` on a host without a global IPv6 address); a v6-only container listener is not the target of an IPv4 DNAT. When the flag was not read, the listener is judged for both families, as before M9, with `bind:v6only unknown (IPv4 judged too)` in its evidence.

- Rules: `nft -j list ruleset`, `iptables-save` and `ip6tables-save`, each bounded to 5 s and 64 MiB. `nft -j` hides the details of iptables-nft's xtables expressions (Docker's `DNAT`, `addrtype`, `conntrack`), so every table that `iptables-save` prints (nf_tables backend) replaces the nft table of the same family and name; native nft tables are kept. With the legacy backend (or when iptables-nft warns that legacy tables exist, then `iptables-legacy-save` too) both rule sets apply. Tables of the bridge, arp and netdev families, and dormant tables, are left out.
- Evaluation: the packet goes through every base chain on prerouting (raw and mangle filters, then NAT, which may DNAT or redirect it), then input when it is for the host or forward when a DNAT sent it elsewhere (the output interface is the one whose connected prefix covers the new destination). Every base chain on a hook must accept it. Jumps, gotos, returns, policies, verdict maps, packet marks set and matched (`MARK`, `meta mark set`), `ct state new` (and `dnat` after a DNAT), `fib daddr type`/`addrtype`, interface globs, port sets and ranges, address prefixes, ranges and named sets are followed. Per-source state is decided for one fresh outside source sending the first packet of a new connection: it is under every rate (`limit`, `hashlimit`, nft `limit`, `meter … limit`, `add @set { … limit }`; a limit on an accept adds `, rate-limited` to the evidence, a `limit … over` never matches), has no `recent` entry (`--set` matches, `--rcheck`/`--update` do not), has one connection (`connlimit`, `ct count`), is in no source set (`-m set … src`, `ip saddr @set`), and sends SYN alone (`--syn`, `--tcp-flags`, `tcp flags`). Matching is three-valued: what the model still cannot decide (`statistic`, a `recent --rdest` list, destination sets, source ports, which the client picks, quotas, unknown modules and statements, a verdict map it cannot read, a jump to a chain the dump lacks, an unreadable NAT target, more than 256 live paths) forks the evaluation, and the answer is open only when every outcome accepts; it is never a definite drop. A source-address match never matches "anyone" unless it covers 0/0; a negated one always does. Concatenated verdict-map keys (`meta l4proto . th dport vmap { … }`) are followed, and `numgen random|inc mod N vmap { … }` (kube-proxy's endpoint choice) takes every element the generator can yield, falling through only when they do not cover it.
- NAT ranges: a DNAT or redirect to an address range or a port range (`--to-destination 10.0.0.1-10.0.0.3:8000-8100`, `REDIRECT --to-ports 9000-9100`, nft `dnat to 10.0.0.1-10.0.0.3:8000-8100`) is simulated: the destination becomes the range, and a port range keeps the packet's own port where it lies inside the range (the kernel's choice for a new connection), else any port of it (always any with `--random`, `--random-fully`, `random`, `fully-random`). Nothing is expanded value by value: a path's destination is an interval, cut only where a later rule's sets start or end, where a host address or connected prefix starts or ends (for the local/forward decision), so each piece decides alike. Outcomes that differ across a range (some backends forwarded, some dropped) are undetermined (`fw:undetermined dnat port range (…)`, `dnat address range`). The evidence names ranges as `nat: dnat tcp/18080 -> 172.17.0.4-172.17.0.5:80`.
- Container listeners: a mapping is a DNAT that a packet from the outside to an external address reaches (found by simulating packets to every port a NAT table matches on, in a rule or in a verdict map's keys; a range of up to 64 ports port by port, a wider one as one packet standing for the whole interval, whose outcomes say which part of it goes where: `nat: dnat tcp/30000-30999 -> 172.17.0.2:30000-30999`), or a host listener held by `docker-proxy`, whose command line (`-host-ip … -host-port … -container-ip … -container-port …`) names its container. A listener in another netns matches a mapping when its port and one of the netns's addresses lie in the mapping's target (an address and port, or ranges; a port-preserving range mapping is judged at the listener's own port) (read from `/proc/<pid>/net/fib_trie` and `if_inet6` of one of its holders) and takes the mapped host port's exposure, with the mapping first in its evidence (`nat: dnat tcp/18090 -> 172.17.0.2:80`, `docker-proxy: 0.0.0.0:18080->172.17.0.2:80`). This covers Docker's iptables and nftables backends, Kubernetes NodePorts in kube-proxy's iptables mode and its nftables mode as laid out by Kubernetes 1.31 to 1.34 (and master as of 2026-11, except its multi-endpoint `dnat … to numgen … map`, which is an unreadable NAT target) (nftables: the `services` chain's `service-ips` and `service-nodeports` maps, `nodeport-ips` or `fib daddr type local`, the service, external and endpoint chains with their `numgen` choice), external IPs that are a host address, and hostPorts (CNI portmap, iptables or its nftables `cni_hostport` table). A ClusterIP-only pod is `bound` with `nat: dnat target … (path not judged)`, as in iptables mode. With kube-proxy present, a pod no host port maps is `bound`, never `local`: pod CIDRs are often routed to the node inside the cluster or beyond it, and an unknown is never lowered. In nftables mode (a `kube-proxy` nftables table) the reason is `fw:undetermined netns mapping (kube-proxy nftables: pod addresses may be routable in the cluster)`; in iptables mode (kube-proxy's `KUBE-SERVICES` or `KUBE-NODEPORTS` chain, read through iptables-save or nft) it is `… (kube-proxy iptables: pod addresses may be routable in the cluster)`. The kubelet's own chains (`KUBE-FIREWALL`, the canaries) do not count, and in IPVS mode, which uses the same chains, the reason is `kube-proxy IPVS mode` alone. A plain Docker container no host port maps is still `local`. An unmapped container listener is `bound` with the reason, not `local`, when its netns addresses cannot be read (`netns: addresses unreadable (…)`; mappings are then matched by port alone), when some DNAT targets it by a path the simulation does not reach (`nat: dnat target 10.0.0.5:80 (path not judged)`), or when the rules hold a mechanism the simulation cannot follow (`fw:undetermined netns mapping (…)`): kube-proxy's IPVS mode (`kube-ipvs0`), Cilium (`cilium_*` interfaces, `CILIUM_*` chains), Docker Swarm's ingress (`DOCKER-INGRESS`), kube-proxy LoadBalancer/external IPs (a DNAT path keyed on a non-host address into `KUBE-EXT-*`/`KUBE-FW-*`, or in nftables mode a `service-ips`/`firewall-ips` element with a non-host address whose verdict goes to an `external-*`/`firewall-*` chain), a DNAT without a port match keyed on such an address or in a NAT base chain, an unreadable NAT rule, or a NAT port range whose simulation went past the path bound (`too many NAT paths`: its mappings may be incomplete). Docker 29 opens published ports in `dockerd` and hands them to `docker-proxy`, so a new mapping's live `opened` names `dockerd`; the DNAT rules still map it.
- Fixtures (`internal/exposure/testdata`, `internal/exposure/nft/testdata`), recorded on Ubuntu 24.04 (nftables 1.0.9, iptables 1.8.10 nf_tables, Docker 29.1.3): a native nft host firewall; Docker's iptables backend (nft JSON and iptables-save); Docker's nftables backend; ufw (deny incoming, a few allows) with Docker; kube-proxy's iptables-mode layout with a NodePort, a CNI hostPort and flannel's forward accepts (written from kube-proxy's chain structure in `kube-proxy.restore`, loaded with `iptables-restore` in a scratch netns and recorded with `iptables-save`/`nft -j`; no cluster was run); kube-proxy's nftables-mode layouts (`kube-proxy-nftables.json` for 1.31: the `ip`/`ip6 kube-proxy` tables with a NodePort service with two endpoints, a ClusterIP-only service and an external IP that is the node's address with the Local traffic policy, plus the CNI portmap plugin's `cni_hostport` table; `-1.34.json`: the 1.34 base chains (`filter-prerouting-pre-dnat`, `filter-output-pre-dnat`, no `filter-output-post-dnat`) and `sessionAffinity: ClientIP`; `-master.json`: master's one-rule `dnat ip addr . port to numgen random mod N map`), written by `testdata/gen/kube-proxy-nftables.py` in `nft -j` form from kube-proxy's `pkg/proxy/nftables/proxier.go` (release-1.31, release-1.34, master) and the portmap plugin's `portmap_nftables.go`, not taken from a live cluster; a container's `fib_trie`/`if_inet6`; docker-proxy command lines.
- Incomplete reads: a source that exists but cannot be read or parsed (permission denied, a timeout, a dump the parser refuses, a missing `iptables-legacy-save` after iptables-nft warned of legacy tables; a tool that is simply not installed is fine) makes the reading partial. Every listener then keeps its last known level, without an `exposure.changed`, and its evidence names the failure (`fw:unreadable iptables-save: Permission denied`); a listener first seen meanwhile is `bound` (`fw:undetermined read incomplete`). The host block's `conditions` carries the failure until a full read succeeds.
- Change detection: the watcher joins the notification groups before its first read. nf_tables changes (including iptables-nft's) arrive on the `NFNLGRP_NFTABLES` netlink group (joining it needs `CAP_NET_ADMIN`), interface and address changes on rtnetlink; each burst is read once it has been quiet for 1 s, and at most 5 s after its first notification, so a steady stream (a busy ban list, a resyncing kube-proxy) still gets read; and a new view is used only if the parsed rules (counters and timestamps excluded) or the interfaces changed. When a notification socket cannot be opened, or an iptables-legacy ruleset is in use (it sends none), the firewall is re-read every `--firewall-poll`. Every `--recheck` a new view is built anyway (it also refreshes container addresses).
- Firewall fingerprint (M7): the agent publishes a digest of the ruleset it judges with, so the backend sees a rule change that moved no listener's exposure (which publishes no `exposure.changed`). It is lowercase hex SHA-256 over a canonical text of the parsed rules (every field written explicitly, addresses and prefixes as text, chains and rules in evaluation order; counters and dump timestamps excluded), so the same rules give the same value in every process, after a restart and on every host; it never contains the rules themselves. The agent stamps it on every host block it publishes (snapshots, listener, exposure, `proxy.routes` and `host.changed` events) as `HostInfo.firewall_fingerprint` (6), and on heartbeats as `Heartbeat.firewall_fingerprint` (12); both are `optional` (unset from older agents). It is set from the view the agent loop is judging with, when that view replaces the last one and before its host block or exposure events go out, so no event of the old ruleset carries the new value. It is set and empty while the firewall cannot be read in full (the `fw:unreadable` condition says why). A fingerprint change on its own publishes nothing new: the next heartbeat (every `--heartbeat`, 30 s) carries it. `portwarden-watch` prints `fw=<first 12 hex>` on `HEARTBEAT` and `SNAPSHOT` lines (`fw=-` when empty, `fw=?` for a value that is not 64 lowercase hex). The inventory stores it per host with `firewall_changed_at` (see "Inventory"). No alert is raised for it.

## Public IP

`internal/publicip` collects candidates (design §5) into the host block:

- `netlink` (`dir=in`): public addresses on up, non-loopback interfaces: not RFC 1918/ULA, CGNAT, link-local, documentation, benchmarking or other reserved ranges.
- `imds` (`dir=in`): the attached public addresses from cloud metadata, plus `cloud` and `instance_id`. The cloud is detected from DMI (`/sys/class/dmi/id`: `sys_vendor` "Amazon EC2" or an Amazon BIOS, "Google Compute Engine", or Microsoft with Azure's chassis asset tag); only then is `169.254.169.254` asked, in the background (startup never waits), with 2 s per request and no proxy: AWS IMDSv2 (token, `instance-id`, `public-ipv4`, `ipv6`), GCP (`instance/id`, `instance/zone`, `project/project-id`, `network-interfaces/?recursive=true`; the response must carry `Metadata-Flavor: Google`), Azure (`/metadata/instance?api-version=2021-02-01`, including `compute.resourceId`). The cloud's full name for the instance goes out as `cloud_resource` (M10). It is refreshed every `--recheck` and retried every 30 s while it fails. `--imds off` disables it.
- `ingest-local` (`dir=out`): the local address of the agent's TCP connection to NATS, only when it is public, i.e. when no NAT is in between and it is the address the server connects out from. Behind NAT the true outbound address is only visible on the server side; filling it in (nats-server sees each client's address) is left to the M5 backend.

## Proxy mapping

`internal/proxy` (design §3): every listener holder whose executable is `nginx` (also OpenResty), `apache2`/`httpd` (an `httpd` must carry Apache's compiled-in `HTTPD_ROOT`; BusyBox's `httpd` does not), `haproxy`, `caddy`, `envoy` or `traefik` is a proxy. Its processes are grouped under the master, the root of its same-executable process tree; one proxy instance per master.

Trust (`discover`, `mapper`): a proxy's config is read only when its master runs as root (effective uid 0), the executable it runs (`/proc/<pid>/exe`) is root-owned and not group- or other-writable, and every config file read is root-owned and not group- or other-writable (checked on the open file, through the proxy's root). Otherwise the proxy is published without routes and with the note `config:untrusted <why>` (e.g. `master runs as uid 1000`, `/etc/nginx/x.conf owned by uid 1000`), and an untrusted master gets no connect hook either: any program named nginx started by an unprivileged user gets nothing read, published as routes or traced.

Where the config is (`internal/proxy/discover`, nothing executed): nginx's `-c` from the master's command line (nginx rewrites it to `nginx: master process <argv>`), else `--conf-path=` compiled into the binary, else `conf/nginx.conf`; a relative path is under the prefix (`-p`, else the compiled `--prefix=`, else nginx's `/usr/local/nginx/`), so OpenResty and source builds find their own config; only a binary without any configure arguments falls back to `/etc/nginx/nginx.conf`; Apache's `-d`/`-f`/`-D` from the command line, else ` -D HTTPD_ROOT=`/` -D SERVER_CONFIG_FILE=` compiled into the binary, else Debian's `/etc/apache2/apache2.conf` or RHEL's `/etc/httpd/conf/httpd.conf`, with `${VAR}` taken from the master's environment (Debian's `APACHE_*`); HAProxy's `-f` files and directories (every `*.cfg`, in order), else `/etc/haproxy/haproxy.cfg`. Files are read as the proxy sees them: from `/` when it shares the agent's mount namespace, else through `/proc/<pid>/root`, with `openat2(RESOLVE_IN_ROOT)` so a container's absolute symlinks stay inside it (`internal/proxy/rootfs`). Reads are bounded per proxy: 20 000 filesystem operations (every read, stat and directory entry looked at), 4096 files tried (failures count), 4 MiB per file and 2 MiB in all (a load's heap peaks at up to 27 times what it reads, and a container's image controls its config; 16 MiB took 276 MiB, past the agent's 256 MiB Kubernetes limit), include depth 32, 4096 matches per include pattern, 32 768 entries per directory, 64 notes (then `... and N more notes`) and 4096 watched paths; a limit cuts the load off with one note. An include of a file already being included (by device and inode) is refused with `include cycle at <path>`, as nginx and Apache refuse it. Whatever cannot be read becomes a note on the proxy (`unreadable /etc/nginx/x.conf: permission denied`), and the rest is still parsed.

Redaction: before anything is published, URL userinfo becomes `***@` and query strings are dropped (target, backend address, notes); a `return` publishes its status code only; Apache targets are published as written, before `${VAR}` substitution, so environment values never are (they are still used to resolve the backend); HAProxy ACLs appear by name only and anonymous `{ … }` conditions folded. Host, port and path are kept.

- nginx (`internal/proxy/nginx`): the tokenizer follows `ngx_conf_read_token` (quotes, escapes, `#` comments, `${var}`); `include` is spliced in place, relative to the main file's directory, with glob(3) semantics (sorted, no dotfiles; a missing plain include is a note). Routes: per `server` (its `listen`s, default `*:80`, and `server_name`s), every `location` (nested too) with `proxy_pass`, `fastcgi_pass`, `uwsgi_pass`, `scgi_pass`, `grpc_pass` or `memcached_pass` (also inside `if` and `limit_except`, noted as conditional), else `return`, else static with its `root`/`alias`; `upstream` blocks give the servers (`backup`, `down` noted); `stream` servers too (`/udp` for UDP listens). Only a target's host[:port] has to resolve: the URI is cut at the first `/`, `?` or URI variable (`$request_uri`, `$uri`, `$args`, `$is_args`, `$1`…), userinfo is dropped, and `$scheme` stands for http or https. Variables in the host are expanded when each has known values (`map` values, `set`), up to 64 combinations; otherwise the backend is `unresolved: variable $x`. `unix:` sockets become Unix backends.
- Apache (`internal/proxy/apache`): directives per line (continuations joined), `Include`/`IncludeOptional` relative to `ServerRoot` (wildcards; a directory is read recursively, sorted), `<IfModule>` decided from the `LoadModule`s seen so far plus the static modules, `<IfDefine>` from `-D` and `Define`, false sections skipped unread; `<If>`/`<ElseIf>`/`<Else>` are read and their routes noted as conditional; `<Macro>` is not expanded (a note). Routes: per `<VirtualHost>` (addresses, `ServerName`/`ServerAlias`) and for the main server (its routes are inherited by every virtual host, as a note says): `ProxyPass` and `ProxyPassMatch` (also inside `<Location>`/`<LocationMatch>`; `!` exclusions skipped), `RewriteRule … [P]`, `SetHandler "proxy:…"` (PHP-FPM in `<FilesMatch>`), `balancer://` with its `BalancerMember`s, `unix:/path|scheme://` sockets, and the `DocumentRoot` as a static route. Default ports follow mod_proxy (`fcgi` 8000, `ajp` 8009, `scgi` 4000, `uwsgi` 3031).
- HAProxy (`internal/proxy/haproxy`): per `frontend`/`listen`, its `bind` addresses and one route per `use_backend` (the condition as the path, its ACL definitions as notes; a `%[…]` backend is unresolved) plus the `default_backend` (also inherited from `defaults`; in a `listen` section it wins over the section's own servers, as HAProxy does); `server`/`server-template` addresses (`unix@`, absolute paths, `ipv4@`/`ipv6@`; no port means the client's destination port, unresolved).
- Names resolve without DNS: IP literals, `localhost`, and the proxy root's `/etc/hosts`; any other host name stays `unresolved: hostname … (no DNS lookups)` and is matched by observed traffic only.

Joining (`proxy.Join`, in the agent loop after every listener change and every mapper update): a route's `frontends` are the proxy's listeners its `listen` addresses are served on (a specific listen address may be served by a wildcard socket). A backend address ends at a listener with the same protocol and port: in the proxy's netns an exact bind, else a wildcard bind when the address is loopback or one of that netns's own addresses; in another netns (a container) a listener whose netns owns the address (container addresses from `/proc/<pid>/net/fib_trie` and `if_inet6`). A remote address is never joined to a local listener. Unix-socket backends report their path only. Observed destinations mark the backend `seen` (with `connections` and `last_seen`); the ones the config does not name become `inferred` routes, one per local listener they reach (its addresses as backends) and then one per other destination, at most 64 per proxy, the rest folded into one `other destinations` route with a count. A destination unseen for three recheck intervals (an hour without a recheck) is forgotten, so a backend left behind by a config change stops showing. Health checks (HAProxy `check`, Apache `hcheck`) are connections too: they make a backend `seen` without client traffic. A `[::]` listener is joined for IPv4 destinations as if dual-stack (an `IPV6_V6ONLY` one, nginx's default for `[::]`, is over-joined, as for exposure). Counts are kept by the kernel per (tracked tgid, destination); the mapper adds each key's growth and sums them per proxy, so they survive reloads.

Reload detection (`internal/proxy/mapper`, every `--proxy-poll`): the fingerprint (device, inode, size, mtime) of every file read, every directory an include globbed and every missing include target; a change that then holds still for 2 s (counted in polls: with the default poll, the next poll that sees it unchanged) re-reads the config (`trigger=config`); a new master pid (a restart, seen through the listener table) re-reads at once (`listener`); the recheck re-reads every proxy and the namespace addresses. A config edited but not (or unsuccessfully) reloaded is reported as written, with the proxy note `pending reload: …` while the newest config file read is more than 1 s newer than the proxy's oldest living worker (every nginx, Apache and HAProxy reload replaces all workers; `/proc/<master>/task/<master>/children` and their start times). A proxy without workers never shows it. A failed connect-hook attach or pid update is retried every poll and shown as the note `observed connections unavailable: <error>` meanwhile.

Fixtures (`internal/proxy/*/testdata`, recorded on Ubuntu 24.04 with nginx 1.24.0, Apache 2.4.58, HAProxy 2.8.30 by `dev/proxy-fixtures.sh`): the distro defaults, and hand-written configs (nginx: virtual hosts, upstreams, conf.d and sites-enabled symlinks, a dotfile the glob skips, every `*_pass`, nested locations, a stream block; maps, `set`, an unresolvable variable, a Unix `proxy_pass`, `if`/`limit_except`, a named location; Apache: name-based vhosts with every construct above, `Define`, `IfModule`/`IfDefine` both ways, an `Include` inside a vhost; HAProxy: ACL-routed `use_backend`, a dynamic backend, inherited `default_backend`, TCP mode, Unix servers, a port-less server, `server-template`, `listen` sections). The tests prove the loaders read exactly the files, in the order and with the content, that `nginx -T` and `apache2 -t -D DUMP_INCLUDES` list, that the Apache parser finds the virtual hosts `apache2 -S` lists, and compare the routes with reviewed golden files (`routes.txt`); the integration tests repeat the loader comparison against the VM's live configs through the `openat2` path.

Process context: every holder is enriched from `/proc` (`exe`, `cmdline`, `sha256` of executables up to 64 MiB, systemd `unit` and `container` from the cgroup). A host-netns listener held by PID 1 (socket activation) gets the owning socket unit as `socket_unit` and its service as `unit`. Socket units are listed over D-Bus (a 2 s attempt before the baseline; afterwards a lookup that misses, or finds the list older than 30 s, starts a background refresh, at most one every 5 s, and is answered from the old list). A listener that systemd opened after the last list, including at boot, when the agent starts before the system bus, gets its `socket_unit`/`unit` at the next recheck (≤ 5 min), as an `owner_changed`. An `owner_changed` is published only when a holder's identity changes: its `pid`, `exe`, `sha256`, `unit`, `socket_unit`, `container` or cgroup. A change of `uid`, `comm` or `cmdline` alone (a privilege drop, a process retitling itself) is no event; the new values appear in the next snapshot and in later events. `comm` is the process's name (the thread-group leader's), also when a renamed thread opened the listener.

### Command-line redaction

Before a holder's `cmdline` is published (in every event, snapshot and proxy route set), the values of well-known secret arguments are replaced by `***` (`internal/redact`); the argument count stays the same, quotes around a masked value are kept, and the agent itself keeps the real command line in memory (proxy discovery reads config paths from it). The argv is read word by word. An argument holding whitespace that is not itself a masked value (a `sh -c` script, a libpq conninfo, a header) is split at any whitespace outside quotes, the separators kept, and read the same way, as a script: commands start after `;`, `&&`, `||`, `|` and `&`, and a command's program is its first word after `sudo`, `env`, `exec`, `nohup`, `time`, `command` and `VAR=value` words. The rules are a fixed table:

| Rule | Masked | Left alone |
| --- | --- | --- |
| Secret flags, one or two dashes, `--flag value` and `--flag=value`: the name (lowercased, `_` read as `-`) is, or ends in `-` plus, `password`, `passwd`, `pass`, `token`, `secret`, `api-key`, `apikey`, `access-key`, `secret-key`, `private-key`; also redis's `--requirepass` and `--masterauth`. The whole next word is masked, spaces and quotes included | `--password hunter2`, `--token=abc`, `-password x`, `--db-password x`, `--auth-token=t`, `--client-secret c`, `--aws-secret-access-key k`, `--api_key=k`, `--password="a b"` → `--password="***"`, `--password 'a b'` | `--password-file /run/secrets/pw`, `--token-path /x`, `--secret-dir=/etc/s`, `--passive 1`, `--keyfile /k`; a following value that starts with `-` (`mysql --password --verbose`: mysql prompts) |
| Per program: mysql-family `-p<password>` (`mysql`, `mysqldump`, `mysqladmin`, `mariadb`, `mariadb-dump` and the other mysql/mariadb clients, also as any command of a script); `redis-cli -a <password>`; `sshpass -p <password>` and `-p<password>`; `curl -u`/`--user`/`-U`/`--proxy-user user:password` (the password part) | `mysql -uroot -phunter2` → `-p***`, `sh -c "cd /tmp && mysql -pX db"`, `redis-cli -a pw`, `sshpass -p pw ssh h`, `curl -u admin:pw` → `admin:***` | `-p` alone, `-P3306`, `-p6379` or `-p 8080` for other programs, `curl -u user` (curl prompts), `redis-server -a x` |
| `Authorization:` and `Proxy-Authorization:` headers: the credentials after a known scheme (`Bearer`, `Basic`, `Token`, `Digest`, `Negotiate`, …), else the next word | `-H "Authorization: Bearer abc"` → `Bearer ***`, `--header=Authorization: Basic dXNlcjpwdw==`, `authorization: abc123` | other headers (`Accept: application/json`) |
| Values (a word, a flag's `=value`, a `VAR=value` before a command): `key=value` items, also in lists split at `;`, `&`, `,` and `?` (URL queries, JDBC and ODBC connection strings, helm `--set`, docker `--env`, kubectl `--from-literal`). A key (letters, digits, `_`, `.`, `-`) is secret when its last dotted segment has a word (split at `_` and `-`, any case, camelCase too) ending in `PASSWORD`, `PASSWD`, `TOKEN`, `SECRET`, `APIKEY` or `AUTHORIZATION`; is `PASS`; is a `PWD` that is not the whole key (a bare `PWD` only inside a list or URL); is `API_KEY`, `ACCESS_KEY`, `PRIVATE_KEY` or `SECRET_KEY`; or, inside a URL or list, ends in `KEY` or is `AUTH`, `SIG`, `SIGNATURE`, `CREDENTIAL(S)`. Java `-D<property>=value` uses the same test | `PGPASSWORD=x`, `MYSQL_PWD=x`, `PASS=x`, `PASSWD=x`, `GITHUB_TOKEN=x`, `AWS_SECRET_ACCESS_KEY=x`, `STRIPE_API_KEY=x`, `password=x` in a conninfo, `--env=DB_PASSWORD=x`, `--from-literal=password=x`, `--set db.password=x,replicas=2`, `--set auth.rootPassword=x`, `https://h/?token=t&api_key=a&key=k`, `jdbc:mysql://db/x?password=p`, `jdbc:sqlserver://db;password=p`, `Driver={X};Uid=u;Pwd=p;`, `-Djavax.net.ssl.keyStorePassword=x` | `PWD=/home/u`, `PASSWORD_FILE=…`, `TOKEN_PATH=…`, `SECRET_DIR=…` (last word `FILE`, `PATH`, `DIR` or `FD`), `TOKENIZER=bert`, `-Dfile.encoding=UTF-8`, `-Dapp.token.ttl=5m`, `?page=2&sort=name` |
| JSON-ish `"key": value` pairs with a secret key (the same test), quoted or bare values | `{"user":"a","password":"p w"}` → `"password":"***"`, `{"token":12345}` → `"token":"***"` | `{"user":"a","n":1}` |
| URL userinfo (`scheme://userinfo@host`) | `postgres://app:pw@db/x` → `postgres://app:***@db/x`, `https://ghp_x@github.com/…` → `https://***@github.com/…` | URLs without userinfo, an `@` in the path or query, `ssh git@host` (no scheme) |

This is best effort: a secret passed in a form no rule knows (a positional argument, an unusual flag or key name, a value split over several arguments, an environment variable, which is never published anyway) is published as is; a list value containing one of `;&,?` is masked only up to it; and an unrelated value can be masked (`--private-key /path` loses its path, a URL query's `sort_key=name`). Prefer files or environment variables for secrets.

Spool: messages are queued in the spool (`internal/spool`, 4 MiB segment files, fsynced) and sent in order; on a restart, messages the last run did not send go out first, with their original `run_id`, `seq` and timestamps. Past `--spool-max` the oldest segment is dropped and counted in the heartbeat's `queue_drops`.

Logs are JSON (`log/slog`) on stderr. The agent exits non-zero, with the reason, when NATS refuses one of its own subjects for lack of permission (credentials minted for another host id: the unit fails and the host goes silent instead of losing every message; a refused `tamper` subject only logs, because it means the auth block was not re-rendered for M6), when the kernel is older than 6.8, `/sys/kernel/btf/vmlinux` is missing, lockdown is `confidentiality`, a BPF program fails to load or attach (the verifier log is included), or the probe reader stops. On SIGTERM it stops the probes, queues its clean-shutdown marker (a `host.changed` with `stopping` set), sends what it can from the spool for up to 2 s and exits 0 (the rest stays in the spool directory and goes out first on the next start, the marker included). An exit on an error sends no marker, so the backend reads it as unclean (`agent_restarted_unclean`). The startup checks live in `internal/preflight`.

### Limitations

- `sha256` is empty for an executable larger than 64 MiB, and for one the agent user cannot read (mode 0711): opening `/proc/<pid>/exe` passes the ptrace check but still needs read permission on the file. `CAP_DAC_READ_SEARCH` would fix the latter and is deliberately not granted.
- A never-seen executable is hashed on the event loop, so a new binary delays the events behind it by its hashing time (bounded by the 64 MiB cap); later events for the same file are answered from a cache.
- `cmdline` is published for every holder and kept in JetStream for the stream's max age (7 days). Well-known secret arguments are masked first (see "Command-line redaction"), but only those the rule table knows.
- The agent's own `exe_sha256` (M11) is empty for the run when `/proc/self/exe` cannot be read at start, or the executable is larger than 512 MiB; the `self_exe` tamper check then takes its own baseline (retried every pass). Version and hash are what the agent says about itself: root can send any values.
- A clean stop's marker that does not leave the host (a full spool, a power cut during the 2 s drain) makes the next start read as unclean: one informational `agent_restarted_unclean`.
- After a power loss the spool may resend messages that were already acknowledged, later than JetStream's 2-minute dedupe window, so consumers should dedupe on `event_id`.
- Exposure is the server's own view: cloud security groups, upstream firewalls and load balancers are invisible to it (levels 3 and 4 are the backend's).
- A view lags a firewall or address change by the debounce (1 s, at most 5 s) plus the read; a listener that opens in that window is judged against the previous view and corrected by an `exposure.changed`.
- A `[::]` listener whose `IPV6_V6ONLY` flag was not read (`bind:v6only unknown (IPv4 judged too)`) is judged for IPv4 too, so a v6-only one's IPv4 exposure would be overstated; every source the agent reads (probe, iterators, inet_diag) reports the flag, so this is only a fallback.
- Interfaces are classified as container networks by name; a real uplink named like one (e.g. `br-wan`) is not treated as external. A netns with its own uplink (macvlan, ipvlan, a moved NIC) is `bound` only when it has a public address, and its firewall is not judged.
- kube-proxy's IPVS mode, Cilium's kube-proxy replacement, LoadBalancer/external IPs that are not a host address and Docker Swarm's routing mesh are not simulated: their pods and tasks are `bound` with `fw:undetermined netns mapping (…)`, never `local`, but are not raised to `host_firewall_open` either. Under kube-proxy's iptables and nftables modes, which are simulated, a pod no host port maps is `bound` the same way: whether pod addresses are routed to the node from elsewhere is not checked. The Kubernetes fixtures reproduce kube-proxy's iptables and nftables layouts but were not taken from a live cluster (the nftables one was written by hand from kube-proxy's source). A DNAT through a map lookup (`dnat to ip daddr map { … }`) is still an unreadable NAT target. A range whose rules cut it into more than 256 pieces on one path is undetermined (`too many paths`; for a NAT range, `too many NAT paths`).
- Upgrading to M9 changes the firewall fingerprint (`fw_digest`, M7) once on hosts whose rules hold a DNAT or redirect to an address or port range, or a `numgen … vmap`: those rules are now read into the model (they used to be unreadable), so their canonical form differs. Other hosts keep their digest.
- An iptables-legacy ruleset also needs `CAP_NET_RAW` to be read (`iptables-legacy-save` opens a raw socket); the unit grants only `CAP_NET_ADMIN`, enough for the nf_tables backend Ubuntu 24.04 uses. Without it the legacy tables appear in the read notes and are left out.
- Rootless containers (rootlessport, slirp4netns, pasta) publish through a host process that is judged as an ordinary host listener; the container's own listener is not linked to it.
- Proxy configs are read from the files, not from the running proxy: a config edited but not reloaded (or whose reload failed) is reported as written (flagged `pending reload` when workers older than the files are running), and an include construct the loaders mis-expand would miss routes (the fixtures check them against the proxies' own dumps; observed connections fill gaps as inferred routes).
- Config files the agent user cannot read (mode 0600, or under `/home`, hidden by the unit's `ProtectHome`) are left out with a note; `CAP_DAC_READ_SEARCH` is still not granted.
- Caddy, Envoy and Traefik configs (their admin APIs) and HAProxy's runtime API are not read: those routes are inferred from traffic only. Apache `<Macro>`s are not expanded.
- Host names in proxy targets are not resolved by DNS (only literals, `localhost`, the proxy's `/etc/hosts`); such backends show unresolved, plus an inferred route once traffic is seen.
- Observed connections are TCP `connect()`s only: UDP upstreams (nginx `stream` with `udp`) are config-only, and Unix-socket backends (PHP-FPM) report their path without traffic or the listening process (Unix-socket tracing is v2). The destination is the one the proxy dialled, so a backend behind NAT or another host is not joined. Counts are per proxy master: they survive reloads, and a destination unseen for an hour is dropped.
- A proxy in the root cgroup (or sharing a cgroup with other programs, e.g. started from a login session) makes the connect programs run for every process in that cgroup; they return after one map lookup unless the process or its parent is a proxy.
- Server names, paths, config file names and redacted targets are published (and kept for the stream's max age, like command lines); redaction removes URL userinfo and query strings, not secrets placed elsewhere in a path.
- Proxies run by a non-root user (or from a user-writable executable, or with config files a non-root user owns or could write) are not mapped beyond their listeners: their routes need a root-run proxy.
- Proxy kinds are recognised by executable name: a renamed binary is not a proxy. A program named like one by an unprivileged user is only listed, untrusted (no config read, no hook).
- HAProxy `.if`/`.endif`, named `defaults` with `from`, `"${ENV}"` addresses and port ranges/offsets are not modelled.

### systemd

`deploy/portwarden-agent.service` (installed by the `.deb` to `/usr/lib/systemd/system`) runs `/usr/bin/portwarden-agent` as the static `portwarden-agent` user with only `CAP_BPF CAP_PERFMON CAP_SYS_PTRACE CAP_NET_ADMIN`, ambient and as the bounding set. `CAP_BPF`/`CAP_PERFMON` load and attach the programs (`bpf_get_current_task` in the connect programs needs `CAP_PERFMON`); `CAP_SYS_PTRACE` reads other users' `/proc/<pid>/exe`, `fd`, `root`, `environ` and `net`; `CAP_NET_ADMIN` reads the firewall (`nft list ruleset` and `iptables-save` fail with "Operation not permitted" without it, as does joining the nf_tables notification group) and attaches the connect programs to cgroups. The `nft`/`iptables-save` children inherit the ambient set. It is `WantedBy=sysinit.target` with `DefaultDependencies=no`, so it starts before the network (design §2); the publisher spools until NATS is reachable. `StateDirectory=portwarden` (mode 0700, owned by the agent user) holds the spool at `/var/lib/portwarden/spool`. Site flags go in `PORTWARDEN_AGENT_ARGS` in `/etc/default/portwarden-agent` (a conffile in the `.deb`). `OOMScoreAdjust=-500` keeps it alive under memory pressure.

Hardening (M6; the M1 review's follow-up): `NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`, `PrivateDevices`, `PrivateIPC`, `ProtectKernelTunables`, `ProtectKernelModules`, `ProtectKernelLogs`, `ProtectControlGroups`, `ProtectClock`, `ProtectHostname`, `UMask=0077`, `RestrictAddressFamilies=AF_UNIX AF_NETLINK AF_INET AF_INET6` (netlink for sock_diag, rtnetlink and nf_tables; Unix for the system bus; IP for NATS and cloud metadata), `RestrictNamespaces`, `RestrictRealtime`, `RestrictSUIDSGID`, `LockPersonality`, `MemoryDenyWriteExecute`, `RemoveIPC`, `SystemCallArchitectures=native` and `SystemCallFilter=@system-service bpf perf_event_open` (`bpf` is in `@privileged` and `perf_event_open` in `@debug`; neither group is allowed whole; `SystemCallErrorNumber=EPERM`). `ProtectKernelTunables` used to be off because it hides `/proc/kallsyms`; the agent does not need it (checked on 6.8 and 7.0: the probes load from BTF). `ProtectProc` stays at its default: the agent reads every process's `/proc` entry. `deploy/units_test.go` pins these directives. `systemd-analyze security --offline=yes` (systemd 255):

The backend units add `SystemCallFilter=@system-service ~@privileged`, `PrivateUsers`, `ProtectProc=invisible`, `ProcSubset=pid`, `ProtectKernelLogs`, `ProtectClock`, `ProtectHostname`, `RestrictRealtime`, `RestrictSUIDSGID`, `PrivateIPC`, `RemoveIPC` and `UMask=0077` to what they had; they run `/usr/bin/portwarden-*`. The e2e (step 11) runs the agent from the real unit with all of it in place.

In the VM, `make install-agent` (`dev/install-agent.sh`) builds the binary, creates the user, installs the binary to `/usr/bin` (earlier versions used `/usr/local/bin`) and the unit, then enables and restarts it. `dev/install-nats.sh` installs `deploy/nats-server.conf` and runs nats-server as a service so there is a broker across reboots. Check with `sudo journalctl -u portwarden-agent` (look for `snapshot queued`: the snapshot is queued for NATS, not necessarily delivered yet; `nats publishing resumed` or a stream message confirms delivery, and `tamper: watching unit files` shows the unit check is on) and `nats stream info ASM_EVENTS`.

Stream: on connect (and after each reconnect) the agent looks up `ASM_EVENTS` and creates it (file storage, `asm.>`, 7-day max age, 2-minute dedupe window) only if it does not exist. An existing stream is used as it is: its retention, replicas and limits are never changed.

Per-host users should only publish `asm.<host>.>` and subscribe to `_INBOX_<host>.>` (`portwarden-natsauth`, see "Backend: NATS users"; `deploy/nats-server-auth.example.conf`; the admin creates the stream, and `$JS.API.>` is admin-level). The agent uses `_INBOX_<host>` as its reply-inbox prefix, so JetStream publish acks arrive there. Never give a host `_INBOX.>`: JetStream consumers receive message payloads on `_INBOX.<id>` subjects, so that would let any host read every consumer's deliveries. The stream lookup is refused for such a user and the agent keeps publishing. A permission violation that does not belong to the request in flight (for example a missing inbox permission, which leaves every publish waiting for an ack) is logged at Warn as `nats permission violation` with its subject.

If messages are dropped because the spool is full (`--spool-max`, e.g. NATS unreachable for a long time), the agent queues a fresh `snapshot` once the spool has drained, as it does after a reconnect. A resnapshot reflects every `opened`, `closed` and `owner_changed` since the last snapshot.

A listener held by several processes (socket-activated sshd: systemd and sshd) lists every holder in the baseline snapshot.

## Tamper signals

These checks catch accidents and clumsy or unprivileged interference with the agent. They do not stop an attacker who has root on the host: see "What root can still do" below. The agent checks itself every `--tamper-interval` (30 s) with fixed rules (`internal/tamper`) and reports what it sees; it never stops or repairs itself. A flag is a kind, a subject and a fingerprint (what was observed: the new content's hash, the tracer's pid, the link's program id); a new fingerprint for the same subject is a new flag and pages again, so a second edit of an already flagged file is never hidden by the first.

| Kind | Subject | Raised when | Cleared when |
| --- | --- | --- | --- |
| `probe_detached` | program name (`on_listen`, `on_connect4@/system.slice/nginx.service`) | the kernel reports a link the agent attached detached: a cgroup link with cgroup id 0 (`bpftool link detach`), a tracing link whose target changed. A proxy restart is not tamper: its cgroup is removed and created again at the same path, the agent sees the new cgroup (a different inode) and re-attaches on its next proxy scan (2 s) | never in this run for an outside detach (the agent does not repair it); a restart re-attaches |
| `program_replaced` | as above | a link runs a program other than the one the agent loaded (`BPF_LINK_UPDATE`): the link's program id differs from the id recorded at attach | as above |
| `ptraced` | `self` | `TracerPid` is set for any of the agent's threads at the moment of a pass | the tracer detaches |
| `binary_replaced` / `binary_missing` | the executable's path | the file at the path `/proc/self/exe` named at start no longer hashes like the running image, or is gone | the file is put back byte for byte |
| `unit_changed` | a unit file | the unit's fragment or a drop-in (systemd's `FragmentPath` and `DropInPaths` over D-Bus, re-read each pass) changed, appeared or disappeared since the check took its baseline | the file is restored |
| `file_changed` | a `--tamper-files` path | that file changed or disappeared | the file is restored |
| `counter_reset` | `ringbuf_drops` | the ring buffer's drop counter (a kernel map) went down: the map was written. Raised for the pass that saw it; a later reset raises again | the next pass |
| `events_dropped` | `ringbuf_drops` | the ring buffer dropped events since the last pass (the agent also rechecks at once). Informational unless the rate reaches `--tamper-drop-rate` (1000 per minute) | a pass with no new drops |
| `upgraded` (informational) | the executable or unit file | the agent's own package replaced it: the marker `/run/portwarden-agent/upgrading` that the `.deb`'s `prerm upgrade` writes is less than 10 minutes old, dpkg's status says that version is being installed, and dpkg's `md5sums` for it list exactly the content on disk. While the upgrade runs and dpkg does not list the file yet, the check reports unknown; anything else is `binary_replaced` / `unit_changed` | the agent restarts onto the new version (`postinst`) |

Informational flags are published and logged (at info level) but never page. A check that cannot read its evidence (D-Bus down, a file unreadable) is reported under `unknown` and keeps its previous flags: it never raises or clears anything. A check that cannot take its baseline yet is retried every pass and reported as `unknown: … not started yet: …` meanwhile, never dropped: at boot the agent starts at `sysinit.target`, before the system bus, and its unit check starts once D-Bus answers (the baseline is the unit files at that moment). Outside a systemd service (a container) the unit check stays `unknown: … not running as a systemd service`. Files are re-hashed only when their stat signature (device, inode, size, mode, mtime, ctime) changes, so a pass costs a few `stat`s, a `/proc` read per thread, one `bpf()` info call per link and two D-Bus calls. Whenever a pass raises or clears a flag the agent publishes a `TamperEvent` on `asm.<host>.tamper` (`raised`, `cleared` and the full `status`); every heartbeat carries the last `TamperStatus` (`flags` with `fingerprint` and `info`, `checks`, `unknown`, `checked_at`, `ringbuf_drops`, and `prog_run_counts` while `kernel.bpf_stats_enabled` is 1). Host NATS users need the new subject: re-render the auth block (`portwarden-natsauth render`) after upgrading; until then the agent logs that its tamper events are refused. A restart of the agent is how an operator accepts a deliberate change to its unit or files. `portwarden-watch` prints:

```
2026-11-03T06:20:41.078Z c1b583b4 seq=3 HEARTBEAT drops=0/0 tamper=ok
2026-11-03T06:20:44.125Z c1b583b4 seq=7 TAMPER raised=ptraced:self cleared=- now=ptraced:self detail=pid 537021 (strace) traces thread(s) 537000
2026-11-03T06:20:45.074Z c1b583b4 seq=8 HEARTBEAT drops=0/0 tamper=ptraced:self
```

What root can still do, unseen:
- Read the agent's NATS credentials (`/etc/portwarden/agent/host.nk`), stop the agent and publish clean heartbeats (`tamper=ok`) and an unchanged inventory from any process: the NATS user is bound to a subject, not to the agent process. Then not even silence shows.
- Change the agent's memory without a tracer: `process_vm_writev(2)` and writes to `/proc/<pid>/mem` need only ptrace access and never set `TracerPid`. With a tracer, it has up to 30 s (the interval) before the next pass sees it, ample to patch the checks or the publisher.
- Act between two passes: a ptrace attach and detach, a `BPF_LINK_UPDATE` and its undo, a file swapped and swapped back within 30 s are missed.
- Replace the binary or unit and restart the agent: the new run starts with a clean baseline. Since M11 a restart without the clean-shutdown marker raises an informational `agent_restarted_unclean`, and the new run's `exe_sha256` shows the new binary, but root can stop the agent cleanly (SIGTERM sends the marker) or publish a forged marker and forged version and hash with the agent's credentials: these are a visibility aid, not attestation. `host_recovered` only follows a silence page.
- Forge the upgrade marker and dpkg's `md5sums` and status, so a swapped binary reads as `upgraded`.
- Load a kernel module, write kernel memory, attach its own BPF programs (another fentry on the same functions, an LSM that hides sockets).

On Ubuntu 24.04 and 26.04 the kernel refuses an external `BPF_LINK_DETACH` of the agent's fentry/fexit links (itest `TestTamperListenLinks`), so only the cgroup connect links can be detached from outside. Built in M11: the alert on a run change without a clean shutdown (`agent_restarted_unclean`), and the running executable's hash and version in every heartbeat and host block (stored per host by the inventory). Ideas for later, not built: compare that hash with the release `SHA256SUMS` in the backend, and `prctl(PR_SET_DUMPABLE, 0)` against same-uid `/proc/<pid>/mem` access.

## Packaging and install

`make dist` (on the host, macOS or Linux; `dev/dist.sh`) builds into `dist/`:

- `bin/linux_{amd64,arm64}/portwarden-{agent,inventory,alerter,verifier,natsauth,watch}`: static (`CGO_ENABLED=0`), `-trimpath`, `-buildvcs=false`, `-ldflags "-s -w -buildid= -X …/internal/version.Version=<version>"`.
- `portwarden-agent_<version>-1_{amd64,arm64}.deb`: `/usr/bin/portwarden-agent`, the unit in `/usr/lib/systemd/system`, `/etc/default/portwarden-agent` (conffile). `postinst` creates the `portwarden-agent` system group and user (also when the group already exists) and handles the unit as `dh_installsystemd` does, with `deb-systemd-helper` and `deb-systemd-invoke` (Depends `init-system-helpers`): enabled and started on a fresh install; on upgrade an administrator's disable or mask is kept and the agent is restarted only if it was running (`try-restart`). `prerm upgrade` writes `/run/portwarden-agent/upgrading` (the new version) so the running agent reports the replaced files as `upgraded` instead of tamper, and `postinst` removes it; `prerm remove` stops the unit, `postrm remove` masks it, `purge` forgets its state and removes `/var/lib/portwarden`. Recommends `nftables`, `iptables`.
- `portwarden-backend_<version>-1_{amd64,arm64}.deb`: the inventory, alerter, verifier, natsauth and watch binaries, their units (installed, not enabled: each needs its config first; running ones are restarted on upgrade), and the example configs in `/usr/share/doc/portwarden-backend/examples/`.
- `sbom/portwarden-<cmd>_linux_<arch>.cdx.json`: CycloneDX SBOMs from each binary's embedded module list (`cyclonedx-gomod bin`).
- `SHA256SUMS` over all of it.

The version is `VERSION=…` when given, else the latest `v*` tag (plus `+git<YYYYMMDDHHMMSS>.<sha>` past it, the commit time first so successive builds sort upward in dpkg), else `0.0.0~git<YYYYMMDDHHMMSS>.<sha>`. `DIST_DIR` may not be `/`, `$HOME` or a top-level directory. File times inside the packages are the last commit's (`SOURCE_DATE_EPOCH`). `make dist-check` rebuilds everything in a temp directory and diffs `SHA256SUMS`: the binaries and `.deb`s are byte-identical between two builds, and between a macOS and a Linux host (checked: an arm64 Mac and the arm64 VM give the same 16 binaries and 4 packages); the SBOMs are identical on one host but record the hash of the `cyclonedx-gomod` binary that wrote them, which differs per host. nFPM v2.46.3 and cyclonedx-gomod v1.12.0 run through `go run`/`go install` at those versions (no new `go.mod` entries). `make dist-lint` (in the VM) checks `SHA256SUMS`, lists each package's control fields and files, runs `lintian --fail-on error` (it passes; warnings remain for no man pages and the changelog stub) and checks each binary's architecture.

Install on Ubuntu 24.04/26.04 (`amd64` on x86_64, `arm64` on ARM):

```bash
sudo apt install ./dist/portwarden-agent_<version>-1_amd64.deb      # enables and starts portwarden-agent
sudo install -d -m 0750 -o root -g portwarden-agent /etc/portwarden/agent
sudo install -m 0640 -o root -g portwarden-agent host-<machine-id>.nk /etc/portwarden/agent/host.nk
echo 'PORTWARDEN_AGENT_ARGS="--nats-url tls://nats.example:4222 --nats-nkey /etc/portwarden/agent/host.nk --tls-ca /etc/portwarden/nats-ca.pem"' | sudo tee /etc/default/portwarden-agent
sudo systemctl restart portwarden-agent && journalctl -u portwarden-agent -f
sudo apt install ./dist/portwarden-backend_<version>-1_amd64.deb    # then configs in /etc/portwarden, see "Backend"
```

Kubernetes: `deploy/Dockerfile` builds the agent image from `dist/` (Ubuntu 24.04 with `nftables` and `iptables`; the base is not pinned by digest, so only the binary in it is reproducible: `docker buildx build --platform linux/amd64,linux/arm64 -f deploy/Dockerfile -t <registry>/portwarden-agent:<version> .`; set the image tag yourself, `appVersion` and the manifest's `:0.0.0` are placeholders). `deploy/kubernetes/daemonset.yaml` (with its Namespace, labelled `pod-security.kubernetes.io/enforce: privileged`: hostPID, hostNetwork, hostPath and added capabilities are refused under the `baseline` Pod Security level) and the chart `deploy/helm/portwarden-agent` (`helm install portwarden-agent deploy/helm/portwarden-agent -n portwarden --set image.repository=… --set nats.url=…`; label the namespace as above; values: image, `nats.{url,existingSecret,credentialType,credentialKey,singleNode,allowSharedCredentials,caSecret}`, `agent.{heartbeat,tamperInterval,proxyMap,imds,extraArgs}`, `seccompProfile`, resources, tolerations, `spoolHostPath`) run one agent per node with `hostPID` and `hostNetwork`, as root with all capabilities dropped but `BPF`, `PERFMON`, `SYS_PTRACE`, `NET_ADMIN` (a non-root container user gets no effective capabilities from a pod spec), `allowPrivilegeEscalation: false`, `readOnlyRootFilesystem: true`, the runtime's default seccomp profile, AppArmor unconfined (the default AppArmor profile lets a container ptrace-read only its peers, which would hide every host process's `/proc` links), no service-account token, `system-node-critical` priority and tolerations for every taint.

NATS credentials in Kubernetes are per node: mint a host user per node (`portwarden-natsauth mint --role host --host <machine-id>`, the node's `/etc/machine-id`) and put every seed in one Secret, each under its file name `host-<machine-id>.nk` (`kubectl -n portwarden create secret generic portwarden-agent-nats --from-file=users/host-<id1>.nk --from-file=…`). The agent runs with `--nats-nkey-dir` and uses its own node's seed, so a node can still publish only under its own `asm.<host>` prefix. A node without its seed fails to start (a crash-looping pod, visible), and an agent whose publishes NATS refuses exits. The chart refuses to render a single seed (`credentialType: nkey`) unless `nats.singleNode=true`, and a shared creds user (`credentialType: creds`) unless `nats.allowSharedCredentials=true`: **a creds user allowed `asm.*.>` lets any compromised node forge any other node's listeners, heartbeats and tamper status.** Mounts: `/sys/fs/bpf` and the host's `/sys/fs/cgroup` (read-only), `/etc/machine-id`, `/run/dbus`, a hostPath spool at `/var/lib/portwarden-k8s` (not the `.deb`'s `/var/lib/portwarden`, so a node running both never shares a spool; created `0755 root`), a memory `emptyDir` on `/tmp`, and the NATS Secret. In the container the agent finds its cgroup namespace root and maps `/proc` cgroup paths to host paths, so units, containers and the proxies' cgroups still resolve. Checked: `make lint-deploy` (helm lint, kubeconform -strict on Kubernetes 1.33 schemas for three value sets, and the refused ones), and the image run in the VM with Docker the way the pod spec runs it. Not checked on a real cluster; the container's `nft` may be older than a 26.04 host's.

### VM verify from any checkout

The VMs mount only `~/projects/portwarden`, so `make itest`, `make e2e` and `make matrix` only test that checkout. `dev/vm-verify.sh` runs the matrix for any checkout (a Flowryn worktree, a verify checkout, another `git worktree`):

1. It copies the checkout's files (`git ls-files --cached --others --exclude-standard`: tracked files and new files not ignored, so uncommitted work is tested; plus any generated BPF objects; no `.git`, no `.matrix/` or `dist/`) into a fresh `~/projects/portwarden/.vmverify/<short-sha>-XXXXXX/` (gitignored), with tar (symlinks kept as links; `dev/vm-verify.sh --copy-only` makes a copy, prints its path and keeps it). `VMVERIFY_ROOT` names another mounted directory.
2. With the `amd64` leg it runs `make dist` in the copy first (log: `.matrix/dist.log`), so the `.deb` lifecycle check runs; git there reads this checkout's history (`GIT_DIR`), so the version is this branch's. `SOURCE_DATE_EPOCH` and `COMMIT` are read from this checkout once, at copy time, so a commit made here during the run does not change what the copy builds. `dev/dist.sh` builds nFPM and cyclonedx-gomod from the Go module cache first (`GOPROXY=file://$(go env GOMODCACHE)/cache/download`) and reaches the module proxy only when the cache lacks them: `go install pkg@version` asks the proxy about a tool's package path even when its module is cached, so a slow proxy used to fail `make dist`, and the amd64 leg's `deb` check, at random.
3. It runs the copy's own `dev/matrix.sh` (`MATRIX_LEGS` from `--legs`), so the copy is the repo under test, and prints the matrix's per-leg summary. It exits non-zero when any leg fails.
4. On exit the logs and `summary.txt` go to this checkout's `.matrix/` and the copy is removed (`VMVERIFY_KEEP=1` keeps it for debugging).
5. On any failure (make dist, a leg, an interrupt) the logs are also kept in `~/projects/portwarden/.vmverify/logs/<short-sha>-<UTC time>/`, which outlives a checkout Flowryn removes, and the path is printed (`vm-verify: failed; logs kept in …`), followed by the last 40 lines of each failing log (`dist.log`, or per the summary a leg's `itest.log`, `e2e.log`, `tests.log`, `dist-upgrade.log` and `deb.log`; every log when the matrix did not finish), so Flowryn's verify log shows why. The newest 20 log directories are kept (`VMVERIFY_KEEP_LOGS`).

**VM lock.** `dev/matrix.sh` (and so `dev/vm-verify.sh`), `make itest` and `make e2e` take a host-wide lock, `~/projects/portwarden/.vmverify/lock/` (`dev/vmlock.sh`; a directory, since macOS has no `flock`), whose `owner` file names the holder (pid, checkout, branch, start, command). A second run prints `vmlock: waiting for the VMs (…); held by: …` every 5 minutes and gives up after `VMLOCK_TIMEOUT` seconds (default 5400). A lock whose owner process is gone is taken over (`vmlock: took over a stale lock: …`). Tests started by hand inside a VM take no lock, so before each leg (and before `make itest`/`e2e`) the VM is checked with `pgrep` for `e2e.sh`, `itest.sh` or a running `*.test` binary, and the run waits while one is found. Remove a lock by hand only when its owner is not running: `rm -r ~/projects/portwarden/.vmverify/lock`.

**In Flowryn.** Add it as the last step of the project's verify list, after the Mac-side steps, and allow about an hour (three legs; the emulated x86_64 leg is the longest):

```toml
[projects.portwarden]
verify = ["go test ./...", "GOOS=linux go vet ./...", "GOOS=linux go vet -tags integration ./...", "dev/vm-verify.sh"]
verify_timeout_min = 60
```

(The first three entries stand for the steps already there.) A verify run that finds the VMs held waits for the lock inside that hour; `dev/vm-verify.sh --legs 2404` is a shorter check.

## x86 test checklist

On an x86_64 Ubuntu 24.04 or 26.04 machine (or VM) with sudo, from a checkout of this branch, with nothing of Portwarden installed:

1. Toolchain and test dependencies: `sudo dev/provision.sh` (Go 1.26.3, clang, bpftool, nats-server, natscli, buf, nginx, PostgreSQL, Docker, lintian), then `export PATH=$PATH:/usr/local/go/bin` (or log in again: the profile script is only read at login). 2. Unit tests: `go test ./...`.
3. Kernel integration tests: `dev/itest.sh` (stops an installed `portwarden-agent` for the run). Expect `ok` for every package; `internal/probes` includes `TestTamperListenLinks` (logs whether the kernel refuses an external detach), `TestTamperProxyConnLinks` and `TestTamperRecreatedCgroupIsReattached`.
4. End to end: `dev/e2e.sh` (about 2 minutes). It ends with `e2e: ok`; the M6 lines are `tamper: <n> heartbeats with tamper=ok, no TAMPER event, no tamper page`, `hardened unit: user portwarden-agent, CapEff 000000c000081000, Seccomp 2; …`, `proxy restart: links … -> …, no tamper`, `tamper ptrace:`, `tamper unit:`, `tamper executable:`, `tamper detach:` and `tamper pages:`. On exit it puts back (or removes) the `/etc/systemd/system/portwarden-agent.service` and `/usr/bin/portwarden-agent` it used.
5. Packages: `make dist` (or copy `dist/` from where it was built and run `sha256sum -c SHA256SUMS` inside it), then `dev/dist-lint.sh`.
6. Package lifecycle: build a second, higher version (`ARCHES=amd64 SBOM=0 VERSION="$(ls dist/portwarden-agent_*_amd64.deb | sed 's/.*agent_\(.*\)-1_amd64.deb/\1/')+upgradetest" DIST_DIR=/tmp/pw-dist2 dev/dist.sh`) and run `dev/deb-check.sh dist/portwarden-agent_*_amd64.deb /tmp/pw-dist2/portwarden-agent_*_amd64.deb`. It ends with `deb-check: ok`.
7. Install for real: start NATS first (`dev/install-nats.sh`; with the default URL `nats://127.0.0.1:4222` the agent needs no flags, and without NATS it only spools), then `sudo apt install ./dist/portwarden-agent_*_amd64.deb`. `systemctl status portwarden-agent` is active, `portwarden-agent --version` prints the version, `journalctl -u portwarden-agent` shows `started` and `tamper: watching unit files`. `go run ./cmd/portwarden-watch --since 2m` shows `SNAPSHOT` and `HEARTBEAT … tamper=ok` every 30 s, and `python3 -m http.server 8111` gives `OPENED tcp 0.0.0.0:8111` within a second.
8. Tamper by hand: `sudo strace -p $(systemctl show -p MainPID --value portwarden-agent) -o /dev/null` for a few seconds gives `TAMPER raised=ptraced:self` and, after it exits, `cleared=ptraced:self` (within 30 s). Edit the unit file systemd actually uses: `f=$(systemctl show -P FragmentPath portwarden-agent); echo '# x' | sudo tee -a "$f"` gives `raised=unit_changed:$f`; a second edit (`echo '# y' | sudo tee -a "$f"`) raises a new flag. Undo with `sudo apt install --reinstall ./dist/portwarden-agent_*_amd64.deb` (restarts the agent).
9. Proxy restart: `sudo apt install nginx` (if not there), wait 5 s, `sudo systemctl restart nginx`, wait a minute: no `TAMPER … probe_detached` line, and `sudo bpftool link show` lists two `cgroup` links for the new nginx cgroup id.
10. Reboot: `sudo reboot`; afterwards `journalctl -b -u portwarden-agent` shows `started` early in boot and, once the system bus is up, `tamper: watching unit files`; the next `HEARTBEAT` lines show `tamper=ok` (and `portwarden-watch` shows no `unknown` unit check after the first minute).

## Backend

Three services read `ASM_EVENTS` (design §1), each as its own NATS user through its own durable consumers, so a restart resumes where it stopped. Configs are JSON files (`--config`, unknown keys refused, durations as `"90s"`); examples in `deploy/*.example.json`, systemd units in `deploy/portwarden-{inventory,alerter,verifier}.service` (`DynamicUser`, no capabilities, secrets passed as systemd credentials). Logs are JSON on stderr. Each needs the stream to exist (created by the admin, subjects `asm.>` and `pwb.>`); until then it waits.

### Subjects and NATS users (`portwarden-natsauth`)

Hosts publish under `asm.<host>.<kind>`, only the agent's kinds. Backend verdicts live in a namespace no host can publish to: `pwb.cloud.<host>.exposure` (the inventory's cloud look-up, an `ExposureEvent`), `pwb.verifier.<host>.exposure` (the verifier's result, an `ExposureConfirmation`) and `pwb.probe.<host>.request` (the inventory asking the verifier to probe, a `ProbeRequest`) and `pwb.inventory.<host>.forgotten` (the inventory announcing a forgotten host, a `HostForgotten`, M8). Consumers take a message's origin from its subject, never from its body: an `asm` exposure event whose body claims an origin, an `asm.<host>.exposure.confirmed`, or a body naming another host than its subject is quarantined as a forgery.

`portwarden-natsauth mint --dir D --role host --host <machine-id>` (or `--role inventory|alerter|verifier|admin`) writes `D/<name>.nk` (the nkey seed, 0600, never overwritten: copy it to the host as `--nats-nkey`, or name it in a service's `nats.nkey_file`) and `D/<name>.json` (public key and role). Host ids `inventory`, `alerter`, `verifier` and `admin` are refused (they would share a service's reply inbox). `portwarden-natsauth render --dir D --out /etc/nats/portwarden-users.conf` writes the `authorization` block for every minted user; `include` it from the server config and reload (`deploy/nats-server-auth.example.conf`). Permissions (`internal/natsauth`, tested against an embedded server loaded from the rendered config):

| User | Publish | Subscribe |
| --- | --- | --- |
| `host-<id>` | `asm.<id>.listener.opened`, `.listener.closed`, `.listener.owner_changed`, `.exposure.changed`, `.snapshot`, `.heartbeat`, `.proxy.routes`, `.host.changed`, `.tamper` | `_INBOX_<id>.>` (its JetStream acks) |
| `inventory` | JetStream info, stream info, single-message get on `ASM_EVENTS` (gap reload), create/info/delete/next/ack on consumer `pw-inventory` only, `pwb.cloud.*.exposure`, `pwb.probe.*.request`, `pwb.inventory.*.forgotten` | `_INBOX_inventory.>` |
| `alerter` | JetStream info, stream info, consumers `pw-alerter` and `pw-alerter-hb` only | `_INBOX_alerter.>` |
| `verifier` | JetStream info, stream info, consumer `pw-verifier` only, `pwb.verifier.*.exposure` | `_INBOX_verifier.>` |
| `admin` | `$JS.API.>`, `$JS.ACK.>`, `asm.>`, `pwb.>` (stream management; never for a host) | `_INBOX.>`, `asm.>`, `pwb.>` |

No service may publish under `asm.>`. A host cannot look up or create the stream, so the admin creates it first. No user but the admin gets `_INBOX.>`. JWT/operator mode works too (creds files), with the same permissions.

### Consuming (all services)

A message is handled once at a time, in order. A transient failure (database or NATS unavailable) is retried in place (backoff 1 s doubling to 30 s, 6 attempts), then NAKed with a 30 s delay so the consumer moves on; consumers have `MaxDeliver` 10. A data error (undecodable, a forged origin, a value the database rejects: SQLSTATE classes 22 and 23) or a message still failing on its last delivery is quarantined (the inventory stores the raw subject, stream sequence, error and bytes in its `quarantine` table) and terminated, so one bad message never stops the fleet's feed. Strings are cleaned before they are stored (NUL bytes removed, invalid UTF-8 replaced), since PostgreSQL rejects both.

### Inventory (`portwarden-inventory`)

Consumes `asm.>`, `pwb.cloud.*.exposure`, `pwb.verifier.*.exposure` and its own `pwb.inventory.*.forgotten` (durable `pw-inventory`, from the start of the stream on first run) into PostgreSQL. Schema and migrations are embedded (`internal/inventory/pg/migrations`) and applied at start under an advisory lock, idempotently; every query is parameterized. Tables: `hosts` (cloud identity, region, cloud resource (M10, migration 0005), public IPs, conditions, current run and last seq, boot id and run number, retired runs, `needs_resync`, last snapshot and heartbeat, silence, cloud status), `listeners` (current listeners with processes, `behind_proxy`, the agent's level and evidence, the cloud's, the last probe, and the effective `level`: the highest of the agent's, 4 when the cloud says open, 5 when the last probe confirmed), `exposure_history`, `proxies`, `quarantine`, `forgotten_hosts` (M8). Upgrading to M8: re-render the NATS users (`portwarden-natsauth render`), since the inventory needs its new `pwb.inventory.*.forgotten` permission; and expect the first start to take longer on a large `exposure_history`, because migration 0004 builds its `at` indexes at start, inside the migration transaction (not `CONCURRENTLY`), with the table locked meanwhile.

- Sequence (design §6): per host the run and last seq are stored in the same transaction as each message's effect, so a redelivery is skipped. A gap within a run reloads the host's latest snapshot straight from the stream when it is at or past the gap, otherwise the message is applied and the host is marked `needs_resync` until its next snapshot. A snapshot replaces the host's listeners (keeping cloud and probe data of those still there) and proxies.
- Runs: the agent stamps every message with the kernel `boot_id` and a `run_number` it keeps in its spool directory (`run-number`, incremented at each start). A run from another boot, or a higher number in the same boot, is the new run; the previous run id is retired (the last 8 are kept) and its late messages are skipped. Wall-clock time plays no part, so a clock that stepped back between runs cannot hide a host. Agents without numbers (before the M5 fix wave, or `--spool-dir ""`) fall back to the run id's ULID order.
- Firewall fingerprint (M7, migration 0003): `hosts.firewall_fingerprint` is the last fingerprint an agent sent, read from heartbeats and from the host blocks of snapshots, listener, exposure and `host.changed` events (not `proxy.routes`; backend events never set it). Only `""` or 64 lowercase hex characters are accepted; any other value is ignored (the rest of the message still applies) and logged once per host. `""` (the agent could not read its firewall in full) is unknown, not a value: the last good fingerprint is kept and `firewall_changed_at` does not move, so it moves only for a real rule change; whether the firewall is readable now is in the host's `conditions` (`fw:unreadable …`). `firewall_changed_at` is the stream time of the message that first carried the new value, i.e. when the backend saw it, not when the rule was changed (up to one heartbeat later, or later still after an outage). First sight sets both; the same value again (including after an agent restart or reboot) leaves `firewall_changed_at`. Messages are applied in the run order above and stale ones skipped, so a late message cannot roll it back. An agent downgraded to one without M7 sends none, and the last value stays in place. Both are `null` in the API until an agent sends a non-empty one. A change is not an alert.
- Silence: a host is silent when the inventory itself has received no heartbeat from it for `silent_after` (default 90 s), measured on the inventory's own clock. When nothing arrives from any host for `silent_after`, or NATS is disconnected, the feed is stalled: no host is judged until messages flow again plus one more `silent_after` (also right after start), so a backend outage never marks the fleet silent.
- Probe requests: after an agent exposure change or a cloud verdict for a listener at `bound` or above, and every 10 min for listeners not probed for `reprobe` (24 h), the inventory publishes `pwb.probe.<host>.request` built from its stored state: the bind address when it is a specific one, otherwise the host's stored inbound public-IP candidates of the bind's family (IPv6 alone for a `::` listener the agent marked `bind:any (IPv6 only)`); the listener's port or a mapped container listener's host ports; at most 4 addresses and 4 ports. Requests wait in a bounded queue (1000); when it is full one is dropped and counted.
- API (default `127.0.0.1:8740`; a non-loopback `listen` is refused unless `allow_insecure_listen`, since the API has no TLS and the token would cross the network in cleartext; every `/v1` request needs `Authorization: Bearer <token>`, compared in constant time over SHA-256 digests; token at least 16 characters, from `PORTWARDEN_INVENTORY_TOKEN` or `token_file`; this read token only reads): `GET /healthz` (no auth), `/v1/hosts?limit=&cursor=`, `/v1/hosts/{id}` (each host with `cloud_resource` when the agent sent one (M10), `firewall_fingerprint` and `firewall_changed_at`, see "Firewall fingerprint" above, and `tamper` and `tamper_at`, see "Tamper status"), `DELETE /v1/hosts/{id}?force=` (admin token only; see "Forget a host"), `/v1/listeners?host=&proto=&port=&addr=&min_level=&unit=&exe=&limit=&cursor=` (`min_level` a level name or 1–5), `/v1/exposure-history?host=&key=&limit=&cursor=`, `/v1/proxy-routes?host=&proxy=`. JSON only, `Cache-Control: no-store`; errors are `{"error": "…"}` without database details.
- Paging (M8): `/v1/hosts`, `/v1/listeners` and `/v1/exposure-history` return at most `limit` rows (1 to 10 000, default 1000) in a fixed order: hosts by id; listeners by host, protocol, port and key; history newest first (time, then row id, so equal times keep their order). `/v1/hosts` with neither `limit` nor `cursor` returns every host, unpaged, as before M8; the other two were already bounded by their default `limit` of 1000. When more rows follow, the response carries `X-Next-Cursor: <cursor>` and `Link: </v1/…?…&cursor=<cursor>>; rel="next"`; the body stays a JSON array. Pass the cursor back as `cursor=` with the same other parameters for the next page; there is no next cursor on the last page. Paging is keyset-based: rows added or removed between pages neither repeat nor shift the others. A cursor is opaque (base64url of the last row's sort key, not signed: it only says where a page starts, never what a client may see) and belongs to its list; a mangled cursor or another list's is `400`. The paged queries were checked for correctness, not tuned: they are fine at the current scale, but a filtered listener page over a very large fleet may scan more than it returns.
- Tamper status (M8, migration 0004): `hosts.tamper` is the agent's latest tamper status, from its `asm.<host>.tamper` events and heartbeats, applied in the run and sequence order above (a late message of an earlier run never rolls it back). The API shows it as `tamper: {flags: [{kind, subject, detail, since, fingerprint, info}], checked_at, checks, unknown, ringbuf_drops}` (the agent's per-program run counts are not kept) and `tamper_at`, the stream time of the message that last changed it; both `null` until an agent sent one. A status equal to the stored one but for its `checked_at` (every tamper pass) is not written again, so `tamper.checked_at` is from that message too, not the last pass; a late status of an earlier run never rolls it back. After a sequence gap the reload from the latest snapshot does not carry tamper status: it is current again with the next heartbeat. A heartbeat without a status (an agent with `--tamper-interval 0s` or before M6) leaves it; a tamper event without one means all checks pass. Consuming tamper events also keeps the host's sequence whole: before M8 the inventory skipped them, and each one left a gap (`needs_resync` until the next snapshot).
- Agent identity (M11, migration 0006): `hosts.agent_version`, `hosts.agent_exe_sha256` and `hosts.agent_stopped_at`, from heartbeats and the host blocks of snapshots and `host.changed`: the latest message wins (an older agent writes `''`). The values come from the host, so the version loses control and non-printable characters and is cut to 64 bytes, and a hash that is not 64 lowercase hex characters is stored as `''` (logged once per distinct value per host, without the value). `agent_stopped_at` is the stream time of the run's clean-shutdown marker and goes back to null with the next message of a running agent; the marker itself starts no cloud look-up. `/v1/hosts` and `/v1/hosts/{id}` return `agent_version`, `agent_exe_sha256` (`""` when unknown) and `agent_stopped_at` (null while running), behind the same token. Self-reported: not attestation.
- Forget a host (M8): `portwarden-inventory forget-host <host-id>` (or `DELETE /v1/hosts/{id}`) removes a decommissioned host. It needs the separate admin token (`api.admin_token_file`, or `PORTWARDEN_INVENTORY_ADMIN_TOKEN`; at least 16 characters, not the read token): without one configured the call answers `403` "forget disabled", and the read token always gets `403`. Stop the host's agent first: a host that is not silent (no `silent_since`) is refused with `409` unless `?force=1` (CLI `--force`); an unknown host is forgotten anyway (`existed: false`), since the alerter may still hold state for it. Every call is logged with the token kind, the host and `force`. The shipped unit loads no admin token, so forgetting stays off until you enable it: create `/etc/portwarden/inventory-admin.token` (0600, `openssl rand -hex 24`), add a drop-in with `LoadCredential=admin-token:/etc/portwarden/inventory-admin.token`, and set `api.admin_token_file` to `/run/credentials/portwarden-inventory.service/admin-token`; run the CLI as root with `--token-file /etc/portwarden/inventory-admin.token`. The inventory first publishes `pwb.inventory.<host>.forgotten` (a `HostForgotten`) and takes its stream sequence from the ack, then in one transaction deletes the host's row, listeners, proxies and exposure history and records the mark (that sequence and the stream's identity, its creation time) in `forgotten_hosts`, and stops judging the host's silence. It waits at most 15 s (and never past the request's own deadline) for the message being handled. From then on any message of the host stored in the stream before the mark (a late or redelivered one) is skipped, as is a cloud or verifier verdict about it until it sends again (a look-up started before the forget). A message from its agent after the mark makes the host new (new `first_seen`, a new run, its next snapshot fills it in). The inventory also consumes its own announcement, so if the database step failed after the announcement (the call then answers `503`), the forget is applied when the consumer reaches it; running it again is also safe. If the announcement cannot be published (NATS down, or the stream not read yet at start), nothing changes and the call fails (`503`). Marks belong to one stream: at start, marks of another stream (one deleted and created again, whose sequences start over) and marks past the stream's last sequence are dropped, so a host id reused on a new stream is not skipped. The alerter reads the announcement in its heartbeat consumer (see "Alerter"). The CLI calls the running service's API: it reads `listen` and `api.admin_token_file` from `--config` (default `/etc/portwarden/inventory.json`; a wildcard `listen` is reached on loopback), `--url` and `--token-file` override them, and `PORTWARDEN_INVENTORY_ADMIN_TOKEN` wins over the file. It prints `{"host", "existed", "stream_seq"}` and exits 1 on any error (the server's message, e.g. "host is not silent"). Host ids must be one plain subject token (they become one). Quarantined messages are not tied to a host and stay until retention removes them.
- Retention (M8): `retention.history` (default `2160h`, 90 days) and `retention.quarantine` (default `720h`, 30 days) prune `exposure_history` and `quarantine` rows older than that; `"0s"` keeps a table forever, and unset or `null` means the default; a negative duration, an `interval` under `1m` or a `batch` outside 1 to 10 000 is refused at start. A pass runs a minute after start and then every `retention.interval` (`1h`), deleting `retention.batch` (1000) of the oldest rows per statement (indexed on time, migration 0004) with a short pause between batches and at most 1000 batches per table per pass, so no statement holds its locks for long and a backlog is worked off over several passes. History ages by the stream time of each change; the current state (the `listeners` table) is never pruned, so a listener stable for longer than `retention.history` keeps its level but loses the history of how it got there.
- Config: `nats`, `postgres_dsn_file` (or `PORTWARDEN_INVENTORY_DSN`), `listen`, `allow_insecure_listen`, `token_file`, `api {admin_token_file}`, `silent_after`, `reprobe`, `cloud {aws, refresh, endpoint, regions, vpn_cidrs, allow_broad, gcp {enabled, key_file, projects, hierarchy_confirmed}, azure {enabled, subscriptions, tenant_id, client_id, client_secret_file, federated_token_file}}`, `retention {history, quarantine, interval, batch}`.

### Cloud look-up (level 3)

With `cloud.aws: true`, `cloud.gcp.enabled: true` or `cloud.azure.enabled: true` the inventory looks up every host whose host block names a cloud: when its listeners, exposure or host block change (after 2 s) and every `cloud.refresh` (10 min). AWS credentials come from the AWS SDK's default chain on the backend, GCP's from `cloud.gcp` (see "GCP"), Azure's from `cloud.azure` (see "Azure"); servers never hold any. Every call is read-only (`deploy/aws-iam-policy.json`). The host-supplied region and instance id are validated (format, and `cloud.regions` when set; at most 64 regions get clients). A region's load balancers are read with their own deadline (3 min), outside any host's 60 s budget, and cached 5 min; a failed refresh keeps the last good data. Calls are paginated with at most 50 pages each and at most 500 load balancers per region.

#### The reach rule: what counts as the internet (M10)

Every cloud rule is judged by the set of source addresses it lets through, not only by whether it names `0.0.0.0/0`. A listener counts as open to the internet unless **every** source address its cloud rules let through is private or inside `cloud.vpn_cidrs` (the user's decision in the M10 design review: "if it's not restricted to VPN then it's on the internet to me"). Private, always: RFC 1918, CGNAT `100.64.0.0/10` and ULA `fc00::/7` (the user's list) and, going beyond it, every other range the IANA special-purpose registries mark as never reached from the internet: loopback, link-local, documentation (`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`, `2001:db8::/32`), benchmarking (`198.18.0.0/15`, `2001:2::/48`), `0.0.0.0/8`, `240.0.0.0/4`, multicast, and IPv6 outside `2000::/3`. The NAT64 prefix `64:ff9b::/96` carries public IPv4 addresses, so it counts as the internet. `cloud.vpn_cidrs` (a list of CIDRs) adds the operator's own VPN egress or office ranges; at start it is refused when a range does not parse, is a `/0`, or is wider than `/8` (IPv4) or `/16` (IPv6) unless `cloud.allow_broad: true`, and the accepted ranges are logged. So **an admin port allow-listed to an office's public IP (SSH from `81.2.69.160/32`, say) counts as open unless that IP is in `vpn_cidrs`**: that is intended. The evidence names the internet ranges that get in (`cloud: sg-web (web) allows tcp/22 from 81.2.69.160/32`; `0.0.0.0/0` or `::/0` when it is all of them, `0.0.0.0/0 except vpn_cidrs 81.2.69.160/28` when the VPN ranges carve some out; at most 4 ranges, then `+N more`), on open, closed and undetermined lines alike. The same rule applies to every cloud layer: security groups, network ACLs and route tables on AWS, GCP firewall rules and policies, and (a later phase) Azure NSGs.

#### AWS

- Direct path (needs the agent's `host_firewall_open`), judged per network interface and per address family: the interface has a public IPv4 (or IPv6); its security groups allow the protocol and port (protocol `-1` is everything) from some internet address (the union of every matching group's ranges and the entries of the managed prefix lists their rules name, so `0.0.0.0/1` plus `128.0.0.0/1` is everywhere; a prefix list that cannot be read, customer- or AWS-managed, that holds an entry without a range, or a range that does not parse makes the path undetermined); its subnet's network ACL lets some of those addresses in (that family's inbound entries in rule-number order, the first entry holding an address decides it, over every range: a narrow deny before a `0/0` allow leaves the rest open, a narrow public allow before a deny-all is open from that range); for TCP, the ACL's outbound entries let replies out to those addresses, judged over every client port 1–65535 since a client picks its own source port: replies allowed on every port 1024–65535 (any ordinary client) keep the path going, replies allowed only on some ports make it undetermined, and none at all close it (UDP is judged on the way in only; an entry that does not parse makes the path undetermined); and the subnet's route table (its explicit association in state `associated`, else the VPC's main table; without a VPC id, undetermined) sends them back through an internet gateway (`igw-`; longest prefix wins, so a more specific route to a NAT gateway takes those addresses away). Only a route to `local`, a NAT gateway, an egress-only gateway (`eigw-`, IPv6), a peering, a blackhole or a confirmed S3/DynamoDB gateway endpoint is not the internet: a public address in a subnet without an internet-gateway route is not reachable. A gateway endpoint delivers only to its AWS service, never to an internet client, so the `vpce-` route (to the S3 or DynamoDB prefix list) that such an endpoint adds is not the internet, but only when the region's `DescribeVpcEndpoints` (type `Gateway`, read with the load balancers and cached alike) lists that endpoint; without the permission, or when the read fails, the route stays undetermined and the evidence says `gateway endpoints not read`. A route to anything else that may forward replies on (a firewall or Gateway Load Balancer endpoint `vpce-`, an appliance interface or instance, a transit, VPN (`vgw-`), local or carrier gateway, a core network, any gateway id not listed here) makes the path **undetermined**, and so does any prefix-list route to an internet gateway or appliance, whatever the CIDR routes say (its ranges are not read, so it may be more specific than a `0.0.0.0/0` to a NAT gateway); only a CIDR route to an internet gateway still makes it open. A security group or ACL that could not be read counts as open (as since M5).
- Load-balancer path (needs only `bound`): an internet-facing ALB/NLB listener whose default action or any rule forwards to a target group holding this instance (by id, or its private IP) on the port, when the LB's security groups (if any) allow the LB port from some internet address (IPv4 or IPv6; a prefix list that cannot be read makes the path undetermined); or an internet-facing Classic ELB with the instance registered and a listener to the port.
- Permissions: `deploy/aws-iam-policy.json` (`ec2:DescribeInstances`, `ec2:DescribeSecurityGroups`, `ec2:DescribeNetworkAcls`, `ec2:DescribeRouteTables` and `ec2:GetManagedPrefixListEntries` (new in M10), `ec2:DescribeVpcEndpoints` (new in the M10 follow-up), and `elasticloadbalancing:DescribeLoadBalancers`, `DescribeListeners`, `DescribeRules`, `DescribeTargetGroups`, `DescribeTargetHealth`), all read-only. Upgrading from M5 without `ec2:DescribeRouteTables`: the host is still looked up, but its direct paths are undetermined until the policy is updated (the status and evidence say `route tables not read: … UnauthorizedOperation`); without `ec2:GetManagedPrefixListEntries`, rules naming a prefix list are undetermined; without `ec2:DescribeVpcEndpoints`, routes to a gateway endpoint stay undetermined. At most 100 prefix lists are read per host: those its own security groups name first, then its load balancers'. Each list is read at most once per region per 5 minutes (the load balancers' cache; at most 1000 lists per region), after the route tables; a failed read (throttling, a denied call, more pages than the page cap) is cached as failed (undetermined) for that window, but one cut short by the host's own time limit is not cached.

#### GCP (M10 phase 2)

Config (`cloud.gcp`): `enabled`; `projects`, the only projects looked up (required: a host naming another project is an error); `key_file`, a service-account JSON key (pass it as a systemd credential, e.g. `LoadCredential=gcp-key:/etc/portwarden/gcp-key.json` and `"key_file": "/run/credentials/portwarden-inventory.service/gcp-key"`). Without `key_file` the inventory uses `GOOGLE_APPLICATION_CREDENTIALS` when set, else the metadata server of the GCE machine it runs on (the machine's service account; `http://169.254.169.254`, `Metadata-Flavor: Google` checked both ways, no proxy). The key's own `token_uri` is ignored. No Google SDK is used: plain HTTPS to the fixed `compute.googleapis.com`, a JWT signed RS256 with the standard library and exchanged at the fixed `https://oauth2.googleapis.com/token` for a `compute.readonly` token (cached until a minute before it expires). None of these hosts is configurable.

```json
"cloud": {"gcp": {"enabled": true, "projects": ["acme-prod"], "key_file": "/run/credentials/portwarden-inventory.service/gcp-key"}, "vpn_cidrs": ["81.2.69.160/28"]}
```

- Permissions: a custom role with exactly `compute.instances.get` and `compute.instances.getEffectiveFirewalls` (`deploy/gcp-role.yaml`; `roles/compute.viewer` also works but is wider), granted on each listed project:
  `gcloud iam roles create portwardenFirewallReader --project acme-prod --file deploy/gcp-role.yaml`, then
  `gcloud projects add-iam-policy-binding acme-prod --member serviceAccount:portwarden@acme-ops.iam.gserviceaccount.com --role projects/acme-prod/roles/portwardenFirewallReader`.
- The host: its `cloud_resource` (`projects/<p>/zones/<z>/instances/<n>`, sent by M10 agents) must name the host block's `instance_id`, a listed project and a zone in the host's region; an agent without it gets `error: gcp: host sends no cloud_resource`. Request paths are built from the parsed parts. `instances.get` (asked by number) must return that same instance id; the effective-firewalls call then names the instance as `instances.get` returned it.
- Every network interface (at most 8; more, or none, is undetermined) gets one `instances.getEffectiveFirewalls?networkInterface=nicN`, with or without an external address, and is judged per family (IPv4 always, IPv6 when it has an IPv6 address). A listener bound to one interface's internal address is judged on that interface only. An interface with an external IPv4 (`accessConfigs[].natIP`) or IPv6 (`ipv6AccessConfigs[].externalIpv6`) whose firewall lets internet sources in is open when the agent says `host_firewall_open` (the direct path, as on AWS). Load balancers and forwarding rules are not read, so wherever the firewall lets internet sources in but the direct path does not count (no external address: a passthrough network load balancer or a forwarding rule may still bring any source, and a proxy load balancer's front ends `35.191.0.0/16` and `130.211.0.0/22` are public; or the agent below `host_firewall_open`), the listener is undetermined (`… only reachable via a load balancer or forwarding rule, not read`). A complete closed verdict means the firewall itself blocks every internet source on every interface.
- Order (Google's "Policy and rule evaluation order"): hierarchical policies (organisation, then folders), system policies, VPC firewall rules and the network firewall policies (global, then regional) in the network's enforcement order, then the implied ingress deny. Within a policy, lower priority numbers first; among VPC rules a deny beats an allow of equal priority; `goto_next` passes traffic on; `apply_security_profile_group` (intrusion inspection) counts as allow. Disabled, egress and non-instance (`targetType` other than `INSTANCES`) rules and rules whose `targetResources` do not name the interface's network are skipped.
- What Google's answer does not say is not guessed: the order of hierarchical policies among themselves, and whether network policies run before or after the VPC rules (`networkFirewallPolicyEnforcementOrder` needs a third permission). Every possible order is evaluated (at most 5 hierarchical policies); an address gets through for sure only if every order lets it through. When the orders disagree the listener is undetermined (`… only if the policy orders Google does not report … disagree`).
- Targets: VPC target tags and service accounts are matched against the instance; policy target service accounts likewise; policy target secure tags may or may not apply (the instance's secure tags are not readable with these permissions). Sources: `sourceRanges`/`srcIpRanges` (a VPC ingress rule with no source field at all is `0.0.0.0/0`, the API default); source tags, source service accounts, source secure tags and `srcNetworkType` other than `INTERNET` never match internet traffic; FQDN, geolocation, threat-intelligence and address-group sources, an unknown network type or action, a range or port that does not parse, and equal priorities with different actions in one policy may match anything. Each of these makes a listener undetermined only when it could decide; otherwise the verdict stands.
- Evidence: `cloud: nic0 (34.68.10.20): firewall allow-https (vpc, priority 1000) allows tcp/443 from 0.0.0.0/0`, `cloud: nic0 (34.68.10.20): policy org-baseline rule 100 (hierarchy) allows …`, `… no rule allows tcp/22 from the internet (0.0.0.0/0); denied by implied deny`, `cloud:undetermined (nic0 (34.68.10.20): tcp/443 allowed from 0.0.0.0/0 only if policy p rule 10 (network) matches FQDN sources)`.
- Hierarchical policies the role cannot read: Google's reference for `instances.getEffectiveFirewalls` (docs.cloud.google.com/compute/docs/reference/rest/v1/instances/getEffectiveFirewalls, read 2026-11-05) names only `compute.instances.getEffectiveFirewalls` and says nothing about whether organisation or folder policies the caller cannot read cause an error or are left out; neither does the firewall-policy documentation. So an answer with no hierarchical policy may be missing one, and an interface judged closed from it is undetermined (`no hierarchical firewall policy was returned …`). Set `cloud.gcp.hierarchy_confirmed: true` once you know the listed projects have no organisation, or that the backend's identity can read the organisation's and folders' firewall policies; open verdicts never depend on it.
- Failures: a token, `instances.get` or check failure is the host's `cloud_status` (`error: gcp: …`, a 403 names the two permissions) and changes nothing; one interface's `getEffectiveFirewalls` failure (or a body over 16 MiB, JSON that does not parse, or a 200 answer holding neither `firewalls` nor `firewallPolicys`) makes that interface undetermined. Target networks (`targetResources`) that do not parse as `projects/<p>/global/networks/<n>` (a numeric id, another format) may name the interface's network: undetermined when decisive. 20 s per request, 60 s per host.

#### Azure (M10 phase 3)

Config (`cloud.azure`): `enabled`; `subscriptions`, the only subscription ids looked up (required; a host in another subscription is an error); and one credential, picked in this order:

- **Client secret**: `client_secret_file` (an app registration's secret, as a systemd credential, e.g. `LoadCredential=azure-secret:/etc/portwarden/azure-secret` and `"client_secret_file": "/run/credentials/portwarden-inventory.service/azure-secret"`), with `tenant_id` and `client_id`. Read once at start.
- **Federated token** (workload identity: AKS, GitHub Actions or another OIDC issuer): `federated_token_file`, or `AZURE_FEDERATED_TOKEN_FILE` when neither file is configured, with `tenant_id` and `client_id` (`AZURE_TENANT_ID`, `AZURE_CLIENT_ID` when empty, as AKS injects them). The file is re-read at every exchange (the issuer rotates it).
- **Managed identity** otherwise: the identity of the Azure VM the inventory runs on, from IMDS (`http://169.254.169.254/metadata/identity/oauth2/token`, `Metadata: true`, no proxy); `client_id` picks a user-assigned identity.

Setting both files is refused at start, as are a subscription or `client_id` that is not a UUID and a missing tenant. No Azure SDK is used: plain HTTPS to the fixed `management.azure.com` (Azure Resource Manager) with a token from the fixed `login.microsoftonline.com/<tenant>/oauth2/v2.0/token` (scope `https://management.azure.com/.default`, cached until 5 minutes before it expires). None of these hosts is configurable, so only public Azure is supported. The start-up log names the credential kind and the subscriptions, never the secret.

```json
"cloud": {"azure": {"enabled": true, "subscriptions": ["0b1c2d3e-4f50-6172-8394-a5b6c7d8e9f0"], "tenant_id": "72f988bf-86f1-41af-91ab-2d7cd011db47", "client_id": "a1b2c3d4-e5f6-4789-8abc-def012345678", "client_secret_file": "/run/credentials/portwarden-inventory.service/azure-secret"}}
```

- Permissions: a custom role with six read actions (`deploy/azure-role.json`: `Microsoft.Compute/virtualMachines/read`, `Microsoft.Network/networkInterfaces/read`, `Microsoft.Network/publicIPAddresses/read`, `Microsoft.Network/virtualNetworks/subnets/read`, `Microsoft.Network/networkSecurityGroups/read`, `Microsoft.Network/locations/serviceTags/read`; the built-in Reader role also works but is wider), assigned on each listed subscription:
  `az role definition create --role-definition @deploy/azure-role.json` (edit its `AssignableScopes` first), then
  `az role assignment create --assignee <app or identity id> --role "Portwarden NSG reader" --scope /subscriptions/<id>`.
  Without `serviceTags/read`, rules naming a service tag other than the four below are undetermined; a missing read action shows as `AuthorizationFailed` in the evidence or status.
- The host: its `cloud_resource` (the VM's resource id `/subscriptions/<id>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<name>`, sent by M10 agents) must name a listed subscription, and the VM read by it must carry `properties.vmId` equal to the host block's `instance_id` and a `location` equal to its region; otherwise the host is an error (`error: azure: …`) and nothing is judged. Request paths are rebuilt from the parsed parts. Every id the backend follows from Azure's answers (NICs, public IPs, subnets, NSGs) is parsed the same way: it must be a Microsoft.Network resource of the expected type in a listed subscription, or that layer is undetermined and it is not requested.
- Reads per host: the VM, each NIC (at most 16; none or more is undetermined), each NIC's public IPs and subnets, and the NSGs on the NICs and subnets. Each IP configuration is one path, judged in its own family (IPv4 or IPv6); a listener bound to one configuration's private address is judged on that one only.
- Order (Microsoft's "How network security groups filter network traffic"): inbound traffic passes the subnet's NSG, then the NIC's, and **both must allow** it; an address range gets through only if both layers let it through. A layer without an NSG does not filter. With no NSG on either layer, a **Standard** public IP admits nothing (closed unless an NSG allows) and a **Basic** one (retired by Microsoft on 2025-09-30, but it may still exist) admits everything; an unknown SKU is undetermined. Within an NSG, inbound rules (the user's and the default `AllowVnetInBound`, `AllowAzureLoadBalancerInBound` and `DenyAllInBound`) by priority, lowest number first; the first that matches decides. Rules match on protocol (`*`, `Tcp`, `Udp`; `Icmp`, `Esp`, `Ah` never match a TCP or UDP listener), destination ports and the destination: the VM's **private** address (Azure translates the public IP before NSGs see the traffic), so `*`, `VirtualNetwork`, a prefix covering the private address, or an application security group the IP configuration belongs to.
- Sources: `*`, `Any` and `Internet` are every address; `VirtualNetwork` and `AzureLoadBalancer` are never the internet, except that Azure's `VirtualNetwork` tag also covers the prefixes of user-defined routes, so when the configuration's subnet has a route table (forced tunnelling, `0.0.0.0/0` to an appliance), or its subnet was not read or is missing (whether it has one is not known), `VirtualNetwork` sources (the default `AllowVnetInBound` included) may be any address and make the listener undetermined where they decide (route tables are not read); source application security groups name VMs and never match internet traffic; prefixes and addresses (one or many: augmented rules) are judged by the reach rule. Any other service tag is looked up in the location's service-tag list (`locations/<location>/serviceTags`, read under the host's subscription, following `nextLink`; at most 10 pages of 32 MiB), cached 24 h per location and read on its own 2-minute deadline outside the host's budget; a failed read is cached 10 minutes and a failed refresh keeps the last good list. A tag listed there counts by its prefixes (the evidence names it: `(service tag AzureCloud) allows tcp/22 from 20.0.0.0/8, …`); `AzureCloud`, `AzureFrontDoor.Backend` and similar tags are public Azure ranges, so they count as the internet unless `vpn_cidrs` lists them. A tag missing from the list, a list not read, a source or port that does not parse, an unknown protocol, access or direction, a destination tag other than `VirtualNetwork`, a rule limited to some client source ports (narrower than 1024–65535), and equal priorities with different access may match anything: each makes a listener undetermined only when it could decide.
- Paths: an IP configuration with a public IP of its family whose NSGs let internet sources in is open when the agent says `host_firewall_open` (as on AWS and GCP); below that it is undetermined (`direct path not counted …`). Load balancers, inbound NAT rules, application gateways, Azure Firewall and appliances are not read, and IP-based load-balancer pools, application-gateway pools by IP or FQDN and firewall or appliance DNAT leave no trace on the NIC: so a configuration without its own public IP whose NSGs let internet sources in is **undetermined**, never closed. One in an application-gateway backend (as the NIC says) is also undetermined when its NSGs let in the virtual network or a private range (the gateway connects from its own subnet's private addresses; `AllowVnetInBound` does that unless a rule before it denies). A public IP without an address (a dynamic IP of a stopped VM) is undetermined too. A configuration is closed only when its NSGs keep every internet source out.
- Evidence: `cloud: web-nic/ipconfig1 (20.1.2.3): subnet NSG web-subnet-nsg rule allow-ssh (priority 300) allows tcp/22 from 0.0.0.0/0`, `… no NSG on the NIC`, `… reachable from 0.0.0.0/0`, `… no rule lets tcp/22 in from the internet (0.0.0.0/0) through both NSG layers; denied by NIC NSG web-nsg rule DenyAllInBound (priority 65500)`, `cloud:undetermined (web-nic/ipconfig1 (20.1.2.3): tcp/22 allowed from 0.0.0.0/0 only if … names service tag Foo, not in the westeurope list)`.
- Failures: a token, VM read or check failure is the host's `cloud_status` and changes nothing (token errors carry Entra ID's error code, never the secret); a NIC, public IP, subnet or NSG that cannot be read (a denied call, 429, a body over its cap, JSON that does not parse) makes its paths undetermined. No retries inside one look-up; the next refresh retries. 20 s per request, 60 s per host.

#### Verdicts

- A verdict built from data not read in full (truncated pages, the load-balancer cap, a stale or failed load-balancer read) is marked incomplete: it carries `cloud:incomplete (…)` evidence and may raise a listener to `cloud_open` but never lowers one; the host's `cloud_status` then says `incomplete: …`.
- An **undetermined** verdict (M10: a layer that could not be read, or a rule or route the backend cannot resolve) carries `cloud:undetermined (…)` evidence and neither raises nor lowers the listener: it keeps the level it had. The host's `cloud_status` counts them: `incomplete: N listeners checked, K open, U undetermined (…)`. A load-balancer path that is open still opens the listener.

A listener whose verdict changes gets a `pwb.cloud.<host>.exposure`: `cloud_open` with evidence like `cloud: sg-0abc (web) allows tcp/443 from 0.0.0.0/0`, or its agent level again when it stops being open. Each verdict is published once even while the inventory has not yet consumed it. Unknown clouds and clouds not enabled get `unsupported provider <name>: no level 3 evidence`.

### Alerter (`portwarden-alerter`)

Consumes `asm.*.exposure.changed`, `pwb.cloud.*.exposure` and `pwb.verifier.*.exposure` (durable `pw-alerter`, new messages only on first start) and heartbeats plus tamper events (`pw-alerter-hb` on `asm.*.heartbeat`, `asm.*.tamper` and, since M11, `asm.*.host.changed` for the clean-shutdown marker, so each host's tamper status and runs are judged in the host's order; recreated at every start from each host's last heartbeat and tamper event, a replay that seeds liveness and feeds the tamper rule, whose marks make it idempotent, but never pages `host_recovered`). The same consumer reads the inventory's `pwb.inventory.*.forgotten` (M8), so a forget takes its place in the host's order: the alerter drops the host's silence, tamper, restart and listener dedupe marks, its agent run and probe results in one transaction with the announcement's mark (its stream sequence and the stream's identity; `alerter_forgotten`, migration 0003), then forgets its liveness, so a decommissioned host never pages `host_silent` again (pages already queued are still delivered). Every message of a forgotten host stored before the mark is skipped on both consumers, the start-up replay included, so a restart does not bring the host back, and cloud and verifier verdicts about it are skipped until it has sent an agent message after the mark (persisted as `back`). Its first agent message after the mark makes it a new host: its next silence pages, its first heartbeat pages no `host_recovered`. Each decision re-checks the mark inside its transaction, and a silence noticed for a forgotten host that is not back never pages, so a forget racing a decision cannot leave a stale page or mark. An announcement already applied is not applied again, so a host that came back keeps its new marks. At start, marks of another stream or past its last sequence are dropped, as in the inventory. Its state is in PostgreSQL (`postgres_dsn_file` or `PORTWARDEN_ALERTER_DSN`; its own tables and migrations, so it can share the inventory's database): each decision, its dedupe mark, the listener's last probe result and the page itself are written in one transaction before the NATS message is acked, so no page is lost to a crash or a webhook outage. Run one instance.

| Alert | When |
| --- | --- |
| `newly_reachable` | an agent `exposure.changed` or a cloud verdict whose level reaches `page_level` (default `host_firewall_open`) from below or from unset |
| `confirmed` | a verifier result `confirmed` for a listener whose last recorded result was not `confirmed` (`page_on_confirmed`, default true); reprobes that keep the verdict never page |
| `host_silent` / `host_recovered` | the alerter has received no heartbeat from the host for `silent_after` (default 90 s), on its own clock / a live heartbeat after a silence page (`page_on_silence`, default true); both survive restarts |
| `tamper` | a tamper flag newly present in an agent's `asm.<host>.tamper` event or heartbeat status (`page_on_tamper`, default true; kinds in `tamper_ignore` never page; informational flags such as `upgraded` and `events_dropped` below the agent's rate never page). One page per flag, keyed by kind, subject and fingerprint (`evidence`: `<kind>:<subject>: <detail>`): a flag that stays raised never pages again, a new observation of the same subject does, and once the agent clears it a later raise pages again. Heartbeats are recorded for liveness in memory before any database work, and the database is only touched when a host's pageable flags change, so a PostgreSQL outage does not read as a stalled feed |
| `agent_restarted_unclean` (`severity: info`) | a heartbeat from a new agent run (another `run_id`, not an older run of the same boot by `run_number`) when the previous run reported its `agent_version` and sent no clean-shutdown marker (`page_on_unclean_restart`, default true): a crash, a kill, a power loss, or a binary swapped and restarted. Evidence names both runs (id, boot, counter, version). At most one per host per `dedupe_window`, so a crash loop raises one; a host's first run, a restart out of an agent older than M11 (it never sends the marker) and a forgotten host's return raise none. Each host's current run is kept in `alerter_runs` (migration 0004), so restarts while the alerter was down are judged from the replay. If the alerter was down across a clean restart and the new run also published a `host.changed`, the replay (last message per subject) has lost the marker and one false notice follows |
| `backend_feed_stalled` / `backend_feed_recovered` | the alerter's own feed stops (NATS disconnected, or no heartbeat from any host for `silent_after`) / resumes. Host silence is not judged while stalled, nor for one `silent_after` after it resumes, so a NATS outage pages once, not once per host |

One page per listener per `dedupe_window` (default 1 h) covers `newly_reachable` and `confirmed`, so a port that opens and is then confirmed pages once. `ignore` entries (`host`, `proto`, `addr`, `port`) suppress listener alerts. An outbox worker delivers pages: one JSON line on stdout each (`id`, `kind`, `severity` (only `info`, on `agent_restarted_unclean`), `host`, `at`, `summary`, `listener`, `level`, `previous_level`, `origin`, `evidence`, `processes`, `public_ips`, `probe`, `last_heartbeat`) and, with `webhook.url` (https only, unless `allow_insecure`), a POST with `X-Portwarden-Timestamp`, `X-Portwarden-Signature: sha256=<hex HMAC-SHA256 of "<timestamp>.<body>">` (secret from `PORTWARDEN_ALERTER_WEBHOOK_SECRET` or `webhook.secret_file`) and `X-Portwarden-Alert-Id` (receivers dedupe on it; `alerter.VerifyFresh` checks a signature and its age). A failed delivery is retried with backoff (1 s doubling to 5 min) across restarts, at most `webhook.max_attempts` (20); a 4xx other than 408/429 gives up at once; redirects are never followed.

### Outside checker (`portwarden-verifier`)

Run it outside the servers' networks, from fixed source addresses with a clear reverse DNS name (design §9). It consumes only the inventory's probe requests (`pwb.probe.*.request`, durable `pw-verifier`), never host events, and probes a request's addresses only when they pass its own checks: inside `allow_cidrs` (an empty list refuses to start), and, for a non-public address (RFC 1918, ULA, CGNAT, …), listed for that host in `host_addresses`. For a listener bound to `0.0.0.0`/`::` it also probes the host's `host_addresses`. At most 4 addresses × 4 ports per listener.

- TCP: connect (`timeouts.connect`, 3 s) and read what the service sends first (at most 256 bytes within `timeouts.banner`, 2 s; non-printable bytes escaped). Nothing is sent, except on `http_ports`, which get `HEAD / HTTP/1.0` with the fixed `user_agent` when the service stayed silent; only the status line is read and redirects are never followed. Refused or timed out is `unreachable`.
- UDP: one fixed request per port: DNS (53: `.` NS, no recursion), NTP (123: v4 client request), SNMP (161: SNMPv3 engine discovery), memcached (11211: `version`); any other port gets an empty datagram. An answer is `confirmed`, an ICMP port unreachable `unreachable`, silence `no_response` (open or filtered; never treated as closed).
- One result per listener (the best of its targets; the others in `detail`), on `pwb.verifier.<host>.exposure`. Work runs on a fixed pool (`rate.concurrency`, 16) fed by a bounded queue (`rate.queue`, 1000; a full queue drops the request and counts it); `rate.global_per_second` (5) and `rate.per_host_per_minute` (30) limit the probes; a listener is probed at most every `min_gap` (30 s). Idle state is pruned after an hour.

### Limitations (backend)

- No real cloud account was available: the AWS look-up (security groups, network ACLs, route tables, load balancers) is tested only with handwritten API responses (EC2 query-protocol XML checked against the SDK's deserializers) and stubs. Listener-rule conditions, Global Accelerator, CloudFront, API Gateway and the ranges of prefix-list routes are not judged (a prefix-list route to an internet gateway or appliance makes the direct path undetermined). The route check covers the instance's subnet only, not the load balancer's subnets. The GCP look-up (M10 phase 2) is tested only with handwritten responses (field names after Google's REST reference, read 2026-11-05); it does not judge GCP load balancers, Cloud Armor, routes or Cloud NAT, nor IAP's range `35.235.240.0/20`, which is public and so counts as the internet unless listed in `vpn_cidrs`; rules targeting secure tags and the guesses Google's answer leaves open (policy order) give undetermined, not a verdict. A VM that may be reachable through a GCP load balancer or forwarding rule is undetermined and keeps the agent's level.
- The Azure look-up (M10 phase 3) is tested only with handwritten ARM responses (field names after Microsoft's REST reference, read 2026-11-06; api-versions pinned at Compute `2024-07-01` and Network `2024-05-01`). It does not read load balancers, inbound NAT rules, application gateways, Azure Firewall, route tables or Azure Bastion: a VM without its own public IP whose NSGs admit internet sources (or, behind an application gateway, the virtual network) is undetermined, and so are `VirtualNetwork` sources on a subnet with a route table or on a subnet that was not read. An application-gateway pool by IP address or FQDN, or an Azure Firewall DNAT rule (which rewrites the source to the firewall's private address), leaves nothing on the NIC, so it cannot be detected: when the NSGs admit only `VirtualNetwork` or private sources (the default rules alone do), such a VM shows **closed** (`cloud: <nic>/<ipconfig> (…): no rule lets tcp/<port> in from the internet (…) through both NSG layers`) although the internet may reach it through the gateway or firewall. A gateway pool by NIC is detected (see Paths above); for the rest, check the gateway's and firewall's rules yourself. Only the configuration's own subnet's route table is considered; if Azure also counts other subnets' route prefixes in `VirtualNetwork`, a subnet without one can still be affected. `VirtualNetwork` sources count as never the internet, although the tag also covers peered and on-premises ranges (VPN, ExpressRoute), which may be public. Only public Azure (no Azure China or US Government). VMs of a uniform scale set have no `virtualMachines` resource id: their agents send none that validates (`error: azure: host sends no cloud_resource …`); flexible scale-set VMs are ordinary VMs. The service-tag list is read under the host's subscription but cached per location, so all subscriptions share it.
- The reach rule counts any public source address as the internet unless `cloud.vpn_cidrs` lists it: an allow-list of trusted public addresses must be mirrored there, or its ports page as open.
- NATS permissions vouch for subjects, not payloads: a host cannot speak for another host or forge the backend's verdicts, but it can still lie about itself (its listeners, its public IPs). The verifier probes the public addresses the host's agent reported (inside the allowlist), so a host can name another public address inside the allowlist as its own; keep `allow_cidrs` tight.
- The inventory's and verifier's seeds can publish verdicts for any host; keep them as safe as the admin's. Verdict bodies are not signed.
- The verifier sees only what is reachable from where it runs; a `no_response` UDP result is not evidence either way.
- The inventory stores one probe result per listener. `exposure_history` and `quarantine` are pruned by age only (no size cap), and `forgotten_hosts` / `alerter_forgotten` keep one small row per forgotten host forever.
- The alerter must run as one instance (it recreates its heartbeat consumer at start). The inventory must too: forgetting a host is serialised with message handling inside the process. A stream recreated while either runs is noticed at their next start (marks are checked against the stream identity read at start).
- Forgetting a host whose agent still runs is undone by its next message (it comes back as a new host); stop the agent first. A forget does not cancel pages already queued, and the stream still holds the host's messages until its max age (only their effect is skipped).
- The inventory API has no TLS of its own; put a TLS proxy in front for remote use. It has two roles: the read token reads, the admin token only forgets hosts.
- The tamper status in the inventory is the latest one only; the alerter's pages and the stream are the history.
- Command-line redaction is a fixed rule table (see "Command-line redaction"): secrets in other forms are still published, and messages published by agents before M8 keep their secrets in the stream until it ages them out.

### Limitations (M6)

- Tamper checks run inside the agent and report only: see "Tamper signals" for what a root attacker can still do unseen. A tracing (fentry/fexit) link cannot be detached from outside on 6.8 or 7.0, so `probe_detached` for the listener programs means a kernel that allows it.
- A package upgrade is recognised through the `.deb`'s marker and dpkg's records; an upgrade by other means (copying a new binary over, another package format) reads as `binary_replaced`, by design.
- The unit check needs the system bus: it starts when D-Bus answers (after boot, about when `dbus.socket` is up), and a change made before that is part of its baseline. In a container (DaemonSet) it stays unknown, as do unit names for socket activation when `/run/dbus` is not mounted.
- The DaemonSet and Helm chart are validated against the Kubernetes schemas and the image was run under Docker with the pod's settings, not on a cluster. containerd's default seccomp profile allows `bpf` with `CAP_BPF`; an older runtime may need `seccompProfile: Unconfined`.
- The `.deb`s are not signed and there is no apt repository; `lintian` warnings remain (see "Packaging and install").
- The x86_64 matrix leg on an arm64 Mac is emulated (QEMU TCG); timing-sensitive e2e checks are not run there (only the unit and integration tests and the `.deb`). The 24.04 and 26.04 e2e runs are arm64; on x86_64 they run in CI (not yet run) and in the x86 test checklist.
- The CI workflow has not run (no Actions minutes): its kernel job depends on KVM on the runner and Lima's QEMU driver. Actions are pinned by commit SHA and the Lima tarball is checked against its SHA-256.
- The backend units' run-time hardening (`PrivateUsers`, `ProcSubset=pid`, `ProtectProc=invisible`, the seccomp filter) was checked by starting each binary under those settings with a missing config, not with a real config and credentials (x86 checklist step 11).
